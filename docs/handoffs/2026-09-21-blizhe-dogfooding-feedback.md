# Blizhe: dogfooding Agent Commons владельцем проекта

Дата: 21 сентября 2026. Реальный локальный проект, браузерный UI, ограниченный бюджет прогонов. Это отчёт о наблюдавшемся опыте, а не статус реализации плана Blizhe.

## 1. Краткий вывод

Через UI удалось собрать команду двумя способами, подготовить BASE → TOOL/CONFIG/REASONS, записать сообщение, проверить смену проекта, восстановление черновика и архивирование. Применение шаблона честно сообщает, что ничего не запускает. Стадии доставки сообщения различимы. Эти части продукта работают и заслуживают сохранения.

Два запуска BASE на `codex-builder` завершились до первого вызова инструмента: обязательный MCP не прошёл handshake, хотя preflight и canary были успешны. Диагностика воспроизвела `scoped reviewer files must be regular` на семи вложенных Git-worktree. После конкретного разрешения владельца временно исключили эти пути через `.git/info/exclude`: snapshot-конструктор успешно прочитал 772 файла за 0.201 s. Это обход условия отказа, не исправление Agent Commons.

Третий BASE на `claude-builder` начал работу и ответил в разговоре, но завершился **`needs_operator`**. Агент сообщил о недоступности `/tmp/...` с контрольным манифестом и будущим worktree, а также о командах Git, требующих интерактивного одобрения в headless-сессии. В канонической записи осталось только `runtime_error` / `probe`: две предыдущие попытки записать причину отклонены валидатором. Процесс завершился с кодом 0, но это не успешный BASE. По стоп-условию новые прогоны остановлены; слепого повтора нет.

Главное трение — разрыв между «профиль готов», фактическим запуском и объяснением отказа. Владелец видит необходимость разобраться, но новый инспектор прогона не даёт причины. В ходе прохода использовался CLI. Позже проверена ссылка «Открыть старую панель»: её раздел Runs показывает безопасную диагностику и различие process/delegation. Значит CLI не единственный возможный путь; проблема — разрыв нового рабочего сценария и старой поверхности диагностики.

**BASE пока не принят, TOOL не запущен, независимой проверки нет.** После разрешённой операторской подготовки создан отдельный worktree от свежего origin/main, квалифицированы оба Codex-профиля и через UI запущен четвёртый BASE — первый в новой workspace. В 18:39:44 UTC агент подтвердил чтение сообщения, отправленного уже во время работы. Файл task-catalog.md выбран и загружен в черновик; отправка вложения ожидает отдельного согласия после отказа автоматической проверки Codex. CONFIG/REASONS только подготовлены. Последний контроль исходной работы владельца (18:27:11 UTC): 44 исходные записи, 4914 файлов без изменений, прежние main и SHA. Коммитов, push, PR и Linear mutations оператор не выполнял.

## 2. Роль и ожидаемый путь

Я действовал как владелец Blizhe: выбирал команду, формулировал ожидаемые результаты и ограничения, запускал через панель, читал исходы. Код должны были писать нанятые агенты. Планирование в Commons проводилось по отдельному разрешению владельца; это не перенос live-статусов Blizhe из Linear в Markdown.

Ожидаемый путь: подключить проект → нанять агентов → создать задачи с зависимостями → BASE → проверка и приёмка BASE → TOOL → проверка и приёмка TOOL. CHATRLS/PUBLIC/GRANTS, SQL-политики и связанные PR #31/#32 исключены. Сами PR в этом проходе не исследованы: это было частью невыполненного BASE.

Смещение исследования: обязательные документы прочитаны до UI по заданию; поэтому это не слепой тест новичка. Знание терминала помогло пройти восстановление состояния, которое обычный владелец мог бы не пройти. Периоды ожидания ответа владельца включены в общее календарное время, но не названы задержкой приложения.

## 6. Что сохранить при упрощении

- Создание команды/задач не запускает провайдера. Явное подтверждение после шаблона работает.
- Ограниченный запуск с конкретным исполнителем, свежим контекстом и лимитом времени. Никаких скрытых автоматических повторов.
- Отдельные сущности прогона, независимой проверки точной редакции и решения владельца. Успешный canary не является review Blizhe.
- Зависимости задач: TOOL/CONFIG/REASONS действительно отображаются blocked при незавершённом BASE.
- История не теряется при отмене задачи; основной вид прячет лишнюю историю.
- Доставка сообщения по этапам: записано → очередь → получено → чтение подтверждено → ответ. Запись не выдаётся за прочтение.
- Раздельные черновики проектов в пределах открытого приложения и явное описание потери при reload в разговоре.
- Disabled-кнопка во время записи; серверная проверка ревизии как контракт. Один двойной клик без видимого дубля не доказывает полную идемпотентность.
- Архивирование объясняет, что файлы останутся; создание новой папки показывает точное расположение до подтверждения.

## 8. Дефекты, воспроизведение и ограничения вывода

### UX-01. CLI fallback: PATH не даёт запустить установленный инструмент

**Операция.** В текущей оболочке `agent-commons --version` вернул `command not found`, хотя `~/.local/bin/agent-commons` существовал. После переустановки `uv` также предупредил об отсутствии каталога в PATH. Временное добавление PATH разблокировало команды; shell config не меняли. Это проверенный барьер окружения, не доказанная ошибка установщика. Исходное предположение о старом executable на PATH в этом процессе не подтвердилось.

### UX-02. CLI fallback: принадлежность operational state другой workspace

**Операция.** `doctor` в Blizhe → `Error: operational state belongs to a different Agent Commons workspace`. Остановились по условию владельца. После разрешения использован отдельный STATE_BASE и убран exact STATE_ROOT. Старое operational state не очищалось. Рекомендация по изоляции была технически полезной, но для владельца требует терминала и знания переменных окружения.

### UX-03. CLI fallback: восстановление receipts

**Операция.** Изолированный `doctor` → idempotency v2 migration required и 4 canonical event receipts require reconstruction. После отдельного разрешения восстановлены четыре производные квитанции. Канонические исходные события не переписывались. Следующий и итоговый doctor чистые. В UI восстановление не исследовалось: этот барьер встретился до запуска панели.

### UX-04. CLI fallback: для восстановления неожиданно нужна активная сессия

**Операция.** `receipt reconcile` → `Error: an explicit active session is required for writes`. Подсказки об обновлении сущности не объясняли необходимость `session start`. Пришлось прочитать help и открыть ограниченную сессию оператора без дополнительных capabilities. После этого reconcile сработал. Предлагается в той же ошибке показывать безопасный следующий шаг и цель сессии.

### UX-05. Подключение существующей папки даёт общую ошибку

**UI.** Новый проект → Подключить папку → вручную указать действующий Blizhe → Продолжить. Через 0.312 s: «Не удалось проверить папку. Проверьте расположение и попробуйте снова.» Эта же папка уже открыта как «Готов». Причина и следующее конкретное действие непонятны. **Гипотеза:** срабатывает ветка уже зарегистрированного проекта; серверный reason не исследован. Новый синтетический проект через «Новая папка» успешно создан, поэтому нельзя утверждать, что все способы подключения сломаны.

### UX-06. Глоссарий: агент, роль, специализация, процесс

**UI + документы.** PRODUCT называет людей-подобных исполнителей Agents и объясняет выбор из специализаций; доска предлагает «Нанять роль», а шаблон — «Создать роли и задачи». В библиотеке «Шаблоны проектов» одновременно описываются как «процессы»; часть текста отсылает к «Роли»/«Работа», когда навигация содержит Доска/Задачи/Библиотека/Настройки. RU-доска оставляет Zoom In/Zoom Out/Fit View на английском. Это наблюдаемая неоднородность; не все разные термины обязательно означают ошибку модели данных.

**Предложение:** на владельческом пути выбрать одно основное слово для нанятого исполнителя; техническую роль и runtime-профиль объяснять по месту. Названия пунктов в тексте должны совпадать с реальными пунктами навигации.

### UX-07. Шаблон: полезная честность, но требуется адаптация к каталогу

**UI.** improve-service → заполнить brief и профили → создать. Получены четыре роли и пять задач, подтверждение «Ни один прогон не запущен». Ни одного автоматического запуска не наблюдали. Шаблон включает SRE/security/QA/lead; frontend/backend пришлось нанять отдельно, четыре задачи переписать под каталог, пятую отменить. Это ограничение соответствия шаблона данной работе, не дефект само по себе.

### UX-08. Ручной найм блокируется без действия восстановления

**UI.** Доска → Нанять роль → выбрать frontend → шесть исполнителей disabled. Текст: «Нет актуального наблюдения по этому исполнителю, поэтому подтвердить его нельзя. Обновите доступность исполнителей и проверьте снова.» В самой форме обновить наблюдение нельзя. Шаблон до этого создал роли с теми же профилями. После явных runtime/catalog при рестарте оба ручных найма удались. Профиль reviewer правильно недоступен для неревьюерской специализации — это полезное ограничение, его не нужно убирать.

### UX-09. CLI fallback: readiness и проверочный запуск

**UI/Операция.** Настройки сообщали, что нужен проверочный запуск, но не дали кнопку canary. «Обновить статус» не изменило старую квалификацию после успешных CLI canary. CLI показывал current/qualified. Понадобились `broker --help`, `broker canary --help`, preflight и по одному canary для builder/reviewer. Последние два preflight — обязательная подготовка по заданию; discovery canary-команды и выход из UI — отдельное трение.

**Гипотеза:** разные конфигурации или области состояния давали разные наблюдения. Изолированного доказательства конкретной причины нет. Кнопка обновления должна объяснять, что именно перечитано и какой профиль/конфигурация проверялись, не раскрывая секреты.

### UX-10. P0: настоящий BASE падает, причина не видна в UI

**UI/Операция.** Задача BASE → техлид codex-builder → Fresh → 20 минут → Start run. Первый запуск: `attempt.3CZF5HMWDTZQWPT0KPVGPWP5S0`. После изменения параметров запуска панели — второй: `attempt.6ETYVY6JDBTHHPQHS609FWYD7M`.

В обоих случаях: `failed`, `nonzero_exit`, exit 1, `terminal_tool_calls:0`, `stdout_bytes_seen:0`, `diagnostic_code:provider_nonzero_unknown`, canonical reason `runtime_error`, process/canonical mismatch false. Никакого запроса ввода credentials не было; это не `needs_operator` и не `input_needed`.

Безопасный фрагмент диагностики:

```text
failed to load models cache: missing field `base_instructions` at line 139 column 5
required MCP servers failed to initialize: agent-commons:
handshaking with MCP server failed: connection closed: initialize response
thread/start failed: error creating thread ... (code -32603)
```

Ошибка cache и MCP-ошибка соседствуют в stderr; **не установлено**, что первая вызвала вторую. Строки выше не содержат приватный ответ модели.

В UI показаны failed history, ID, время, свежесть и «полные данные свидетельств», но не причина отказа. На переходе кратко наблюдались одновременно Critical attention required / Provider authentication и Authentication is ready, disabled Continue launch, Another write is being saved. Затем «Run recorded» сообщает факт регистрации, а не успех, но остаётся заметным рядом с уже failed-попыткой.

На этом шаге для выяснения причины использован CLI fallback `broker attempts --diagnostic`. Позже обнаружен альтернативный UI-путь: Настройки → Открыть старую панель → Runs, где есть тот же sanitized stderr. Поэтому отсутствие диагностики относится к новому инспектору, а не ко всему продукту. Карточка решения просит проверить failed run, но не даёт саму диагностику. В инспекторе не нашёл явный повторный Prepare; альтернативы найдены через карточку агента «Дать задачу» и через обсуждение. Третий слепой запуск Codex не выполнялся.

**Критерий улучшения:** владелец из одного failed run видит, началась ли работа, безопасную категорию отказа, точный следующий шаг и факт расхода попытки; диагностика не требует чтения raw private output. Canary должен покрывать реальный способ старта либо честно объяснять границу проверки.

### UX-11. CLI fallback: конфигурация панели и восстановление browser session

**Операция/Код/UI.** Для разблокировки прочитаны Troubleshooting, Broker Operations и `ui --help`; точечно прочитано место CLI, принимающее `--profile-config`. Панель перезапущена с явными runtime.yaml/catalog.yaml. Одноразовый адрес первого перезапуска в прежней вкладке дал `This browser session is no longer active`, `Status code not_found`. После следующего запуска новый одноразовый адрес открыт в новой вкладке; вход успешен. Каждый код использован ровно один раз, в отчёт не записан.

Причина ошибки сессии не изолирована: одновременно изменились запуск панели и вкладка. Не следует объявлять это доказанным дефектом повторного входа. Локальный bind сначала был отклонён sandbox `Operation not permitted`; запуск с разрешённым доступом к loopback сработал. Это ограничение среды выполнения.

### UX-12. Сохранение задач и двойной клик

**UI.** При сохранении REASONS отправлен двойной клик; через 0.346 s кнопка disabled «Сохраняется…». Подтверждение замечено не позднее 7.728 s, видимого дубликата нет. Число серверных событий одного сохранения отдельно не исследовано. Искусственную задержку сети не вводили. Ранняя попытка повторного клика на шаблоне не дошла до UI: инструмент получил Node detached; это не доказательство обработки дубля продуктом.

### UX-13. Доставка: хороший пример честной границы

**UI.** Первое уточнение отправлено между failed-попытками, без активного run. При третьем BASE последовательность достигла «Получено запуском» и «Чтение подтверждено». Позже в разговоре появился подробный ответ Claude; стадия «Ответ записан» достигнута. Агент подтвердил ограничения и чтение каталога по пути. Это фактически пройденная доставка текста, не вложения.

Второе уточнение набрано во время активного BASE. Попытка Add files не дала подтверждённого вложения; разговор закрылся, но черновик сохранился. При возвращении BASE уже needs_operator. Этот текст не отправлен и не считается доставленным во время работы. Задержка появления ответа после завершения наблюдалась, но точная latency не измерена.

### UX-14. Файл не приложен: ограничение браузерного инструмента

**Операция инструмента.** Add images or files → file chooser → `task-catalog.md` → `Not allowed`. Вызов `fileChooser.setFiles` вернулся через 755 s. Документация инструмента требует включить Allow access to file URLs для расширения Chrome; настройка не менялась, пользователю показана инструкция. Открытого native picker после ошибки не было. Исходный UI не подтвердил вложение; сообщение исправлено, чтобы не утверждать обратное.
