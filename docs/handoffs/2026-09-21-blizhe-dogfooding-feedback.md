# Blizhe: dogfooding Agent Commons владельцем проекта

Дата: 21 сентября 2026. Реальный локальный проект, браузерный UI, ограниченный бюджет прогонов. Это отчёт о наблюдавшемся опыте, а не статус реализации плана Blizhe.

## 1. Краткий вывод

Через UI удалось собрать команду двумя способами, подготовить BASE → TOOL/CONFIG/REASONS, запустить работу и независимую проверку, отправить сообщение с файлом, проверить смену проекта, черновики и архивирование. Шаблон честно отделяет создание команды от запуска; разговор различает запись, получение, подтверждение чтения и ответ. Эти части стоит сохранить.

**До принятого результата путь пока не доведён.** BASE.md создан, первый QA вернул `changes_requested` из-за отсутствия точной передачи файлов. Исправляющий агент подготовил два файла baseline evidence, но остановился `needs_operator` на регистрации. После явного согласия владельца оператор зарегистрировал три файла, привязал их к BASE, записал воспроизводимую verification и отправил точную ревизию на повторный независимый review. Каноническое состояние теперь `review`, три artifact bindings актуальны, `artifact_stale:false`.

**Повторный QA ещё не стартовал:** установленный код Agent Commons изменился, прежние успешные canary больше не соответствуют текущим отпечаткам профилей. UI неверно называет это «проверочный запуск завершился ошибкой», хотя receipts обоих Codex-профилей остаются `qualified:true`. Новый model process не запускался. По стоп-условию дополнительных canary запрошено отдельное решение: закрепить отдельную установку из текущего main, затем по одному canary для builder/reviewer. Три согласованных проектных прогона остаются неиспользованными. BASE не принят; TOOL не запускался; CONFIG/REASONS только подготовлены.

Главное трение — разрывы между готовностью профиля, реальной доступностью рабочей папки, передачей результата и решением владельца. Два первых BASE падали до первого вызова MCP; третий Claude BASE остановился из-за доступов. Отдельный операторский worktree позволил создать результат, но передача точных артефактов снова потребовала вмешательства. Новый UI скрывает актуальный отрицательный review и не даёт возврата; помогли старая панель и CLI. При этом независимая проверка не позволила спутать `succeeded` с принятым результатом.

Последний операторский контроль **19:45:15 UTC**: исходный `main/cbdcad62`, 44 записи и SHA256 всех 4914 файлов сохранены; exclude исходный. В изолированной ветке только состояние Commons, BASE.md и два файла baseline evidence. Код приложения не менялся; commit/push/PR/Linear mutations не выполнялись. Doctor: `ok:true`, 49 событий, 3 manifests, `issues:[]`; одно ожидаемое предупреждение о старом review.

Доставка вложения проверена: собственный несекретный `BASE-owner-constraints.txt` отправлен 19:13:54 UTC, агент подтвердил полное чтение 19:20:19 UTC — через 6 мин 25 с в том же прогоне. Более ранний task-catalog.md остался неотправленным из-за внешней auto-review Codex; это отдельно от дефектов Commons. При успешной доставке шапка разговора всё ещё ошибочно говорила «Активного запуска нет».

## 2. Роль и ожидаемый путь

Я действовал как владелец Blizhe: выбирал команду, формулировал ожидаемые результаты и ограничения, запускал через панель, читал исходы. Код должны были писать нанятые агенты. Планирование в Commons проводилось по отдельному разрешению владельца; это не перенос live-статусов Blizhe из Linear в Markdown.

Ожидаемый путь: подключить проект → нанять агентов → создать задачи с зависимостями → BASE → проверка и приёмка BASE → TOOL → проверка и приёмка TOOL. CHATRLS/PUBLIC/GRANTS, SQL-политики и связанные PR #31/#32 исключены. BASE сверил fetched Git refs и явно отметил недоступность живого GitHub API; актуальный remote review/merge state этим не подтверждён.

Смещение исследования: обязательные документы прочитаны до UI по заданию; поэтому это не слепой тест новичка. Знание терминала помогло пройти восстановление состояния, которое обычный владелец мог бы не пройти. Периоды ожидания ответа владельца включены в общее календарное время, но не названы задержкой приложения.

Метки доказательств:

- **UI** — увидено или сделано в браузерной панели.
- **Операция** — вывод CLI, preflight, canary, диагностики или контрольной команды.
- **Код** — точечное чтение реализации/контракта; не доказательство успешного пользовательского пути.
- **Гипотеза** — возможное объяснение или предлагаемое улучшение; требует проверки.

## 6. Что сохранить при упрощении

- Создание команды/задач не запускает провайдера. Явное подтверждение после шаблона работает.
- Ограниченный запуск с конкретным исполнителем, свежим контекстом и лимитом времени. Никаких скрытых автоматических повторов.
- Отдельные сущности прогона, независимой проверки точной редакции и решения владельца. Успешный canary не является review Blizhe.
- Зависимости задач: TOOL/CONFIG/REASONS действительно отображаются blocked при незавершённом BASE.
- История не теряется при отмене задачи; основной вид прячет лишнюю историю.
- Доставка сообщения по этапам: записано → очередь → получено → чтение подтверждено → ответ. Запись не выдаётся за прочтение.
- Раздельные черновики проектов в пределах открытого приложения и явное описание потери при reload в разговоре.
- Disabled-кнопка во время записи; серверная проверка ревизии как контракт. Один двойной клик без видимого дубля не доказывает полную идемпотентность.
- Архивирование объясняет, что файлы останутся; создание новой папки показывает точное расположение до подтверждения.

## 8. Дефекты, воспроизведение и ограничения вывода

### UX-01. CLI fallback: PATH не даёт запустить установленный инструмент

**Операция.** В текущей оболочке `agent-commons --version` вернул `command not found`, хотя `~/.local/bin/agent-commons` существовал. После переустановки `uv` также предупредил об отсутствии каталога в PATH. Временное добавление PATH разблокировало команды; shell config не меняли. Это проверенный барьер окружения, не доказанная ошибка установщика. Исходное предположение о старом executable на PATH в этом процессе не подтвердилось.

### UX-02. CLI fallback: принадлежность operational state другой workspace

**Операция.** `doctor` в Blizhe → `Error: operational state belongs to a different Agent Commons workspace`. Остановились по условию владельца. После разрешения использован отдельный STATE_BASE и убран exact STATE_ROOT. Старое operational state не очищалось. Рекомендация по изоляции была технически полезной, но для владельца требует терминала и знания переменных окружения.

### UX-03. CLI fallback: восстановление receipts

**Операция.** Изолированный `doctor` → idempotency v2 migration required и 4 canonical event receipts require reconstruction. После отдельного разрешения восстановлены четыре производные квитанции. Канонические исходные события не переписывались. Следующий и итоговый doctor чистые. В UI восстановление не исследовалось: этот барьер встретился до запуска панели.

### UX-04. CLI fallback: для восстановления неожиданно нужна активная сессия

**Операция.** `receipt reconcile` → `Error: an explicit active session is required for writes`. Подсказки об обновлении сущности не объясняли необходимость `session start`. Пришлось прочитать help и открыть ограниченную сессию оператора без дополнительных capabilities. После этого reconcile сработал. Предлагается в той же ошибке показывать безопасный следующий шаг и цель сессии.

### UX-05. Подключение существующей папки даёт общую ошибку

**UI.** Новый проект → Подключить папку → вручную указать действующий Blizhe → Продолжить. Через 0.312 s: «Не удалось проверить папку. Проверьте расположение и попробуйте снова.» Эта же папка уже открыта как «Готов». Причина и следующее конкретное действие непонятны. **Гипотеза:** срабатывает ветка уже зарегистрированного проекта; серверный reason не исследован. Новый синтетический проект через «Новая папка» успешно создан, поэтому нельзя утверждать, что все способы подключения сломаны.

### UX-06. Глоссарий: агент, роль, специализация, процесс

**UI + документы.** PRODUCT называет людей-подобных исполнителей Agents и объясняет выбор из специализаций; доска предлагает «Нанять роль», а шаблон — «Создать роли и задачи». В библиотеке «Шаблоны проектов» одновременно описываются как «процессы»; часть текста отсылает к «Роли»/«Работа», когда навигация содержит Доска/Задачи/Библиотека/Настройки. RU-доска оставляет Zoom In/Zoom Out/Fit View на английском. Это наблюдаемая неоднородность; не все разные термины обязательно означают ошибку модели данных.

**Предложение:** на владельческом пути выбрать одно основное слово для нанятого исполнителя; техническую роль и runtime-профиль объяснять по месту. Названия пунктов в тексте должны совпадать с реальными пунктами навигации.

### UX-07. Шаблон: полезная честность, но требуется адаптация к каталогу

**UI.** improve-service → заполнить brief и профили → создать. Получены четыре роли и пять задач, подтверждение «Ни один прогон не запущен». Ни одного автоматического запуска не наблюдали. Шаблон включает SRE/security/QA/lead; frontend/backend пришлось нанять отдельно, четыре задачи переписать под каталог, пятую отменить. Это ограничение соответствия шаблона данной работе, не дефект само по себе.

### UX-08. Ручной найм блокируется без действия восстановления

**UI.** Доска → Нанять роль → выбрать frontend → шесть исполнителей disabled. Текст: «Нет актуального наблюдения по этому исполнителю, поэтому подтвердить его нельзя. Обновите доступность исполнителей и проверьте снова.» В самой форме обновить наблюдение нельзя. Шаблон до этого создал роли с теми же профилями. **Гипотеза / направление улучшения.** Подготовка должна проверять совместимость разрешений с точной рабочей папкой и артефактами задания, показывать безопасную подготовку отдельной копии и отдельно проверять минимальный цикл read/edit/validate. MCP-canary не доказывает доступ к Git, рабочим файлам и командам валидации. Нельзя считать достаточным просто переписать prompt, переключить `acceptEdits` на `dontAsk` или выставить trusted_workspace: это не добавляет каталог/правила. Глобальное отключение проверок не предлагается. Отказы terminal-tool должны оставлять устойчивый безопасный код причины без сохранения приватных аргументов.
