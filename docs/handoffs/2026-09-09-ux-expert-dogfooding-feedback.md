# Agent Commons: handoff UX-эксперту по опыту реального использования

Дата подготовки: 9 сентября 2026 года. Язык: русский.
Автор наблюдений: Codex, работавший над Agent Commons через сам сервис, браузер,
CLI и инструменты провайдеров. Адресат: независимый эксперт по UX/product design.

**Задача эксперту:** предложить, как превратить действующий инструмент координации
агентов в понятное приложение для человека, который хочет создать продукт и
управлять работой команды, а не изучать протокол оркестрации.

Этот файл можно передавать отдельно от переписки. Он содержит контекст,
наблюдения по этапам, ограничения доказательств и ожидаемый результат экспертизы.
Это не новый ADR, не приёмка реализации и не результат исследования с выборкой
пользователей. Предложения ниже — вопросы и гипотезы для проверки экспертом.

## 1. Краткий вывод

Сервис уже полезен: можно организовать проект, собрать роли и задачи из шаблона,
общаться с исполнителями и получать результаты конкретного агента. Основной
разрыв сейчас — между надёжной внутренней моделью и тем, как человек понимает
происходящее. Видимый экран стал проще, но работа всё ещё требует знания
различий между ролью, профилем, запуском, задачей, review и приёмкой.

Три наиболее важных направления следующего прохода:

1. Быстрый и однозначный ответ на действие пользователя, особенно при записи
   изменений в большой проект.
2. Понятная карта **текущей работы**, вместо попытки осмыслить весь накопленный
   граф проекта сразу.
3. Объяснение состояния через результат, следующего ответственного и нужное
   действие человека; технические детали доступны по запросу.

Это приоритеты автора handoff, а не вывод о том, что эстетика уже достаточна.
Отдельный визуальный разбор типографики, плотности, иерархии и компонентов нужен.

## 2. Что это за продукт и чего хочет владелец

Agent Commons — локальный сервис для совместной работы человека и нескольких
агентов над проектом. Провайдер исполнения выбирается отдельно от специализации:
например, одна специализация frontend-инженера может использоваться экземплярами
«Codex Frontend» и «Claude Frontend».

Основные понятия, которые сейчас приходится связывать пользователю:

| Понятие | Практический смысл |
| --- | --- |
| Проект | Рабочая папка и граница задач, агентов, разговоров и результатов |
| Навык | Версионированные инструкции в библиотеке сервиса |
| Специализация | Определение ответственности и используемых навыков |
| Агент / экземпляр роли | Именованный исполнитель с выбранным провайдером и настройками |
| Blueprint / шаблон | Определение команды, задач и зависимостей для типового проекта |
| Задача | Ожидаемый результат, критерии и зависимости |
| Прогон | Конкретная попытка исполнения задачи выбранным агентом |
| Результат | Изображение, артефакт или превью, привязанные к производителю и работе |
| Review / приёмка | Проверка определённой версии и отдельное решение принять результат |

Владелец хочет путь: подключить/создать папку → описать продукт → выбрать шаблон
или команду → запустить работу → видеть живую карту → вмешиваться текстом,
изображениями и файлами → открывать результаты конкретной задачи/агента.
Большая часть этого пути должна быть доступна через UI.

Его исходные претензии, которые **нельзя выдавать за новые наблюдения автора**:

- дублирующиеся подписи Projects / Search Projects и отдельный Project Actions;
- непонятные Team, Context и Open Project Gallery;
- плоский список навыков и незаметное создание собственного Blueprint;
- галерея в общей библиотеке вместо результатов конкретного исполнителя;
- ощущение внутренней панели или Streamlit-приложения вместо цельного продукта.

Часть этих претензий уже адресована реализацией. Эксперту нужно оценить новую
версию, а не автоматически повторять список недостатков старого интерфейса.

## 3. Граница опыта и версия

Основные наблюдения собраны в проходах 8–9 сентября 2026 года. Это смешанный
опыт разработчика-оператора: браузерные действия, операции через Commons CLI/API,
реальные провайдеры и автоматизированные проверки. Знание архитектуры помогало
автору обходить затруднения и создаёт смещение: новичку может быть сложнее.

- Текущий код на момент подготовки: `39459cc5ab051765e8eb559d71798c8256f2c81b`.
- Исправления независимо проверялись на `2a6324c72f5e4ce263fc2ccdd0e30a0db36b6da8`.
  Merge сохранил те же файлы приложения.
- Исходный пакет этой волны сохранён в `405d8c690d3c7e33fedb63828db9d30e6a6185e9`.
- Последний проверенный установленный Work asset: `work-DV06NGBp.js`.
- Часть UI-journeys относится к предыдущему `work-cJnL5_T-.js`; это явно отмечено.
- В заполненном tracker наблюдались 272 задачи. Затем была добавлена одна
  следующая задача производительности; при подготовке документа в ledger 273 задачи.
- Локальный green contract: 2589 Python, 224 Work, 27 Gallery тестов;
  13 документированных Python-пропусков. CI PR и merge-коммита прошёл на обеих ОС.
  Это техническая проверка, а не измерение понятности интерфейса.

**Метки доказательств:**

- **UI** — действие/состояние наблюдалось в установленном браузерном приложении.
- **Операция** — наблюдалось через CLI/API, broker или реальный provider run.
- **Код/тест** — подтверждено реализацией, review или тестом; не полноценным UI-путём.
- **Владелец** — исходное пожелание или оценка владельца.
- **Гипотеза** — интерпретация автора, требующая UX-проверки.

Далее «открыто» означает открытое UX-направление на этой границе, а не отсутствие
всего связанного функционала. «Исправлено» не означает, что весь сценарий прошёл
исследование с пользователями.

## 4. Карта пути и наблюдения

### UX-01. Вход в проект: что я открыл и где будут мои файлы

**Где:** боковая панель проектов, форма создания/подключения папки.
**Этап:** начало работы или переключение между проектами.
**Основание:** Владелец + UI + Код/тест. **Статус:** частично улучшено.

Ожидание: выбрать существующую папку либо создать новую и сразу понимать,
какой проект активен. Операции с проектом должны находиться рядом с его именем.

В браузере прошёл путь создания отдельного проекта через ручной путь. Компактная
панель и меню рядом с названием дали более ясную структуру. Клавиатурный путь
открытия меню, выбора Rename, фокуса в поле и отмены формы проверен на предыдущем
asset. Старое визуальное дублирование подписей было связано в том числе с
отсутствующим CSS для `sr-only`, а не только с информационной архитектурой.

**Оставшийся риск:** ручной путь предполагает понимание файловой системы.
Фактический выбор папки через нативный chooser не был проверен. Не установлено,
сможет ли новичок отличить архивирование проекта в сервисе от удаления его файлов.
Меню не следует описывать как полный аналог Codex/Finder: поддержаны не все
желаемые действия.

**Вопрос эксперту:** как обозначить папку, активный проект и безопасные действия
без постоянного показа технического пути? Как объяснить архивирование до клика?
**Повторить:** новый проект, подключение существующего, отмена chooser,
недоступная папка, повторный клик, переключение при незавершённой форме.

### UX-02. Выбор команды: специализация, агент и провайдер

**Где:** Агенты/Team, специализации, выбор профиля при применении шаблона.
**Этап:** подготовка исполнителей. **Основание:** UI + Операция + Владелец.
**Статус:** функциональная основа есть; понятность требует проверки.

В отдельном тестовом проекте через UI был создан экземпляр роли с Claude-профилем.
Реальные запуски через сервис использовали Codex, Claude и Grok. Однако человеку
нужно связать несколько разных выборов: ответственность, имя, провайдер, профиль,
модель и возможность запуска.

**UX-гипотеза:** настройка исполнителя перегружена внутренними различиями.
Выбор провайдера легко принять за обещание всех его возможностей. Шесть
проверенных runtime-профилей означают builder/reviewer для трёх провайдеров,
а не шесть профессий и не шесть постоянно работающих агентов.

**Вопрос эксперту:** какой минимум выбора нужен в первом проходе? Можно ли сначала
выбирать работу/специализацию, а затем показывать доступных исполнителей с
объяснением ограничений? Какие настройки нужны только в расширенном режиме?
**Критерий понятности:** человек своими словами отличает определение роли от
экземпляра агента и понимает, кто реально начал работу.

### UX-03. Навыки: поиск, организация и обслуживание своей библиотеки

**Где:** Библиотека → Навыки; группы; создание/переименование группы.
**Этап:** подбор и адаптация методов. **Основание:** UI + Код/тест.
**Статус:** группировка улучшена; управление группами не закончено.

Группы раскрываются, есть поиск. В установленном UI проверены создание и
переименование пользовательской группы на двух языках; Enter открывал и закрывал
группу Product and design на предыдущем asset. Это заметно удобнее плоского каталога.

**Конкретная шероховатость:** созданную пустую группу можно переименовать, но
симметричного удаления/архивации группы нет. После проверки осталась тестовая
группа; её не удаляли обходным редактированием приватного состояния.

**UX-гипотеза:** пока не хватает ощущения управляемой личной библиотеки: «я могу
безопасно попробовать, прибраться и понять, какие навыки действительно нужны».
Нельзя считать весь CRUD навыков пройденным в браузере на основании проверки групп.

**Вопрос эксперту:** как различать встроенное и своё, показывать число элементов,
объяснять пустую группу и делать обратимые действия? Нужны ли отдельные режимы
«выбрать навык для роли» и «управлять библиотекой»?
**Повторить:** поиск внутри закрытой группы, пустая выдача, новая пустая группа,
перенос навыка, копия встроенного навыка, удаление группы с содержимым.

### UX-04. Blueprint: от шаблона к реально начавшейся работе

**Где:** Библиотека → Шаблоны проектов, создание/редактирование и применение.
**Этап:** построение команды и начального плана. **Основание:** UI + Код/тест.
**Статус:** ключевые действия прошли; переход к запуску требует упрощения.

В установленном UI проверены создание своего двуязычного Blueprint, применение,
архивирование и сохранение новой версии архивированного шаблона. Применение
создавало роли и задачи. **Оно само по себе не запускало провайдера.**

При авторинге требовались обе локали и точная специализация. Проверялись отказ,
исправление ввода и успешное сохранение. Для технического автора это выполнимо;
затраты новичка на такую форму не измерены.

**Момент возможного непонимания:** пользователь нажал «Создать роли и задачи»,
видит готовую команду и ожидает начала работы, хотя ещё нужен отдельный запуск.
Это гипотеза о восприятии, а не зарегистрированная ошибка запуска.

**Вопрос эксперту:** нужен ли единый мастер с обзором создаваемого плана и явным
следующим шагом? Как дать языковые значения по умолчанию, не скрывая от автора
содержимое шаблона? Как сделать копирование и редактирование легче ручного задания
всех технических связей?

### UX-05. Готовность провайдера и подготовка запуска

**Где:** Настройки runtime, профиль, подготовка прогона, причины отказа.
**Этап:** перед первым реальным выполнением. **Основание:** Операция + Код/тест.
**Статус:** ограниченные live-проверки прошли; объяснение возможностей открыто.

На финальном runtime прошли шесть реальных коротких запусков: builder и reviewer
для Codex/Claude/Grok. Это подтверждает конкретный процесс/протокол, а не любую
способность агента. В более ранних media-проверках провайдер мог прочитать файл
или опубликовать готовую картинку, но не создать новую либо не выполнить нативную
команду сборки. Ограничения Claude/Grok на shell/build остаются отдельным вопросом.

**Урок для UX:** один зелёный индикатор «готов» слишком легко прочитать как
«этот исполнитель сможет выполнить выбранную задачу». Пользователю важна
готовность к нужному действию: читать изображение, писать код, запускать сборку,
публиковать превью, получать новые сообщения.

**Вопрос эксперту:** как показать релевантные возможности до старта, сохранить
простоту и дать понятный выход при ограничении? Как отличать отсутствие настройки,
устаревшую проверку и фактическую ошибку провайдера?

Путаница владельца вокруг «300 секунд» тоже важна: это был лимит одной canary-
проверки, а не глобальный предел работы всех агентов. Лимит попытки и смысл
проверочного запуска должны быть названы в интерфейсе явно.

### UX-06. Настройка прошла, но экран не обновился

**Где:** действие Configure runtime и последующее обновление snapshot.
**Этап:** настройка и восстановление после ошибки.
**Основание:** независимое review + Код/тест, не браузерное воспроизведение гонки.
**Статус:** конкретный баг исправлен.

Последовательность до исправления: первый POST успешно сохранял настройку;
ожидание снималось до завершения GET; второй Configure отменял этот GET;
сервер отвечал `setup_configured`; интерфейс оставался со старой картиной и
предлагал повторить запись. Исправление выполняет заменяющее чтение после этого
определённого отказа; при ошибке чтения повторяет чтение, сохраняя границы проекта.

**Урок для UX:** успешное действие, неудачный запрос и неудачное обновление экрана
нельзя показывать одинаково. Пользователь должен понимать, сохранены ли данные,
можно ли безопасно повторять действие и что именно повторится.

**Вопрос эксперту:** предложить согласованную модель состояний сохранения и
восстановления для всех форм, включая неопределённый исход и смену проекта.
Не предлагать «всегда повторить POST» или оптимистический успех без подтверждения.

### UX-07. Наблюдение за работой: граф становится историей всего проекта

**Где:** Работа → граф/список, фильтры, выбор узла и инспектор.
**Этап:** ежедневный контроль выполнения. **Основание:** UI.
**Статус:** открыто.

На финальном asset tracker показывал 272 задачи и подключённые автоматические
обновления. Фильтрация и выбор R5 с клавиатуры открывали инспектор. Для большого
исторического графа интерфейс направлял к фильтрации/списку; сохранённого вида
конкретной волны из девяти задач не было.

Поиск по общему префиксу названий находил семь задач вместо девяти: две назывались
иначе. Это **не потеря задач**, а показатель того, что текстовый поиск не заменяет
явную принадлежность к цели или волне работы.

**UX-гипотеза:** человеку нужен ответ «что моя команда делает сейчас, что мешает
и где нужен я», а полный ledger отвлекает от него. Большой исторический граф
полезен для расследования, но плохо подходит как единственный домашний экран.

**Вопрос эксперту:** предложить уровни обзора — проект, текущая цель/волна, задача,
исполнитель — и понятный переход между ними. Как сохранить выбор, масштаб и
фильтры при live-обновлениях? Что видно у маленького нового и большого старого проекта?
Не объявлять отображение событий потоком скрытых рассуждений модели.

### UX-08. Инспектор задачи: сначала понять результат, затем детали системы

**Где:** панель выбранной задачи, ожидаемый результат, summary, readiness.
**Этап:** чтение задачи и решение о следующем действии. **Основание:** UI + Код/тест.
**Статус:** несколько конкретных недостатков исправлены.

В раннем UI-проходе цель была свёрнута, а пустой summary занимал место. Также
задача могла выглядеть как имеющая неполное evidence лишь из-за отсутствия
необязательной capacity-телеметрии. Это наблюдалось в браузере и было исправлено:
цель раскрыта, пустой блок опущен, техническая информация убрана в раскрытие,
ложное предупреждение ограничено корректным условием.

**Урок:** инспектор не должен заставлять искать саму постановку среди диагностики.
Отсутствие технической телеметрии не равно отсутствию результата или препятствию
для работы. После исправления остаётся вопрос общей иерархии карточки.

**Вопрос эксперту:** что человек должен увидеть за несколько секунд: цель,
исполнитель, ход работы, последний результат, препятствие, следующий шаг?
Какие детали нужны всегда, а какие только при разборе ошибки?

### UX-09. Human in the Loop: сообщение сохранено — но кто его прочитал?

**Где:** разговор проекта, задачи и отдельного агента; вложения и статусы доставки.
**Этап:** уточнение требований во время работы. **Основание:** UI + Операция + Код/тест.
**Статус:** механизм работает в проверенных случаях; понятность требует проверки.

В task chat наблюдались реальные ответы Grok. На финальном runtime реальный Codex
получил изображение и текстовый файл через MCP, подтвердил сообщение и корректно
ответил на обе проверки содержимого. Это важное подтверждение доставки реальных
данных, но **не доказательство полного пути загрузки через браузерный file chooser**.

Сохранение сообщения не запускает модель. Исполнитель читает сообщения в
поддерживаемых точках; сохранение, очередь, получение, подтверждение и ответ —
разные стадии. Продолжение уже завершившегося процесса не возникает автоматически.
Текущий контракт допускает 10 PNG/JPEG и 10 других файлов, до 15 000 000 байт каждый.
Черновик сохраняется при навигации внутри открытого приложения; перезагрузка
страницы очищает локальный текст, что следует из руководства/контракта, а не нового
эксперимента на потерю черновика.

**UX-гипотеза:** форма чата создаёт ожидание немедленного ответа. Особенно опасны
сообщение неактивному агенту, уточнение на весь проект и ожидание реакции после
окончания прогона. Контекст адресата должен быть очевиден до отправки.

**Вопрос эксперту:** как показать адресата, доступность, доставку и необходимость
нового запуска без перегрузки статусами? Что делать с поздним уточнением,
частично загруженными файлами, неизвестным исходом отправки и перезагрузкой страницы?

### UX-10. Результаты: найти именно то, что сделал этот исполнитель

**Где:** кнопка Результаты у задачи/агента; изображения и отдельные frontend previews.
**Этап:** осмотр результата, сравнение и обратная связь.
**Основание:** Операция + UI + Код/тест. **Статус:** направление подтверждено опытом.

В реальной проверке публикация принадлежала нужному task/agent; у контрольных
посторонних исполнителей результатов не было. В предыдущей финальной версии
браузер открывал отдельное превью после завершения delegation. После изменения
ревизии задачи картинка стала исторической, но открывалась через View recorded
image с проверенными исходными пикселями. Preview при смене точной ревизии задачи
становился stale по действующему контракту.

В этих проверках часть изображений и frontend-страница были созданы тестовым
harness и опубликованы агентом. Это не доказательство, что агент сам спроектировал
и собрал полноценный продукт. В одном автоматическом preview-сценарии истёк таймер
ожидания; отдельное браузерное открытие прошло. Два результата сохранены раздельно.

**UX-гипотеза:** слово Out of date может восприниматься как «работа сломана»,
хотя исторический результат существует. Нужны различия между прошлой версией,
недоступным адресом, истёкшим preview и результатом, ещё не прошедшим review.

**Вопрос эксперту:** как выделять последний результат и объяснять его актуальность?
Нужен ли preview прямо на карточке? Как связать комментарий с конкретной версией
и вернуть человека из отдельной вкладки к нужному исполнителю?

### UX-11. Проверка и приёмка: «готово» имеет слишком много значений

**Где:** task status, review, следующий шаг, итоговая сводка.
**Этап:** завершение работы и решение человека. **Основание:** Операция + UI.
**Статус:** открытая проблема представления; различия состояний намеренные.

Все девять задач волны передавались в review. После нового найденного бага R5/R6
прошли повторный цикл с обновлёнными доказательствами. Новые независимые review
были одобрены; задачи остались в `review`, не `accepted`. Git merge тоже состоялся
отдельно. Значит, «прогон успешен», «задача реализована», «review одобрен»,
«принято» и «влито» в этом продукте действительно не синонимы.

До повторного цикла инспектор R5 предлагал приёмку на основании старого одобрения;
новое противоречащее evidence пришлось учитывать при повторной проверке. Это
наблюдение этапа, а не утверждение, что такое предложение сохранилось после
обновления review-привязок.

**Вопрос эксперту:** как показывать бизнес-смысл состояния и следующий шаг,
сохранив точную проверку ревизии? Нужна ли единая карточка решения человека с
результатом, изменениями, заключением reviewer и причиной блокировки?
Нельзя упрощать статусы путём автоматической приёмки или скрытия нового замечания.

### UX-12. Ожидание действия на заполненном проекте

**Где:** запись изменений, completion/submission/review/handoff; также обновление экрана.
**Этап:** повторяется при управлении работой. **Основание:** Операция, локальные замеры,
статический анализ. **Статус:** главный открытый технический риск для UX.

В предыдущем локальном sample чтение занимало 10,67 с холодным, 0,32 с прогретым;
перестроение графа — 1,36 с. Это отдельный sample старой границы, не p95 и не SLO
текущей версии. Записи через CLI/API оставались существенно медленными.
Полный цикл обновления evidence и переоткрытия/возврата R5/R6 занимал порядка
десятка минут. В него входило несколько операций; это **не замер одной кнопки**
и не доказательство такой же задержки каждого пользовательского сообщения.

Статический review обнаружил повторные полные чтения/валидации events и receipts
под общей write-lock. Причина вклада отдельных этапов ещё не измерена. Создана
следующая ready-задача: `task.6Q4A7HE1QVX4VQKBBSNS8CRZA4` — профиль mutation на
synthetic workspace с разделением lock wait/hold, чтений, replay, append/reconcile.

**Последствие для UX:** даже правильная операция при долгом неопределённом ожидании
провоцирует повторный клик и сомнение в результате. Spinner сам по себе проблему
не решает. При этом нельзя объявлять запись успешной до подтверждения сервера.

**Вопрос эксперту:** какие состояния и возможность продолжать другую работу нужны
во время ожидания? Какие пороги задержки установить как продуктовые цели, а затем
проверить технически? Разделить улучшение обратной связи и реальное ускорение записи.

### UX-13. Визуальная цельность, клавиатура и узкий экран

**Где:** общий shell, библиотека, меню, формы, инспектор.
**Этап:** весь путь. **Основание:** Владелец + ограниченное UI-наблюдение + Гипотеза.
**Статус:** нужен отдельный визуальный аудит.

В предыдущем asset проверены отдельные keyboard-сценарии меню/группы. На узком
viewport в английской и русской библиотеке наблюдались CSS-width и scroll-width
354 px без горизонтального overflow. Это не полная проверка mobile, screen reader,
контраста, focus order и всех ошибок форм.

Моя оценка: компактная панель и группировка уже улучшили ощущение структуры.
Нельзя из этого заключить, что шрифты, цвета и все композиции получили независимое
дизайнерское одобрение. Нет данных, что конкретная гарнитура сама по себе является
главной причиной ощущения «внутренней панели».

**Вопрос эксперту:** оценить типографическую шкалу, плотность, длину строк,
вертикальный ритм, конкурирующие акценты, роль цвета статусов, состояния компонентов
и соотношение основной работы с настройками. Показать изменения на наполненных
экранах, а не только красивом пустом dashboard.

## 6. Что важно сохранить при упрощении

- Раздельность проектов, адресатов, производителей и результатов; чужие outputs
  не должны попадать в красивый общий поток без соответствующего scope.
- Разницу между созданием плана и запуском провайдера.
- Правдивость delivery/read/answer и readiness; отсутствие ack не заменять
  декоративной галочкой «прочитано».
- Идемпотентность, сохранение исходного запроса при неопределённом результате,
  защиту от устаревшего ответа после переключения проекта.
- Точную версию результата/review и отдельную приёмку человеком.
- Доступ к истории без выдачи исторического результата за текущий.
- Приватное хранение вложений и отдельный origin недоверенного preview.
- Двуязычность, доступные названия элементов, keyboard/focus и ограничения файлов.

Человеку не обязательно постоянно видеть эти термины. Но UI должен сохранять
их смысл и безопасно объяснять исключения.

В этот handoff **не вложены screenshots**. В предыдущем проходе экраны
просматривались через браузер, но не были сохранены как отдельный версионированный
набор снимков. Ниже — задание на съёмку, а не утверждение о наличии готовых картинок.

| Кадр | Состояние, которое нужно показать |

Для основных кадров снять EN/RU и узкое состояние там, где меняется компоновка.

Локальный адрес приложения — `http://127.0.0.1:8787/work`: он доступен только на
машине, где запущен сервис, и не является ссылкой для удалённого эксперта.
Для удалённой экспертизы передать безопасный визуальный пакет или предоставить
отдельную демонстрационную среду, не отправляя учётные данные.

## 8. Какие сценарии дать независимому пользователю

Это предлагаемый протокол будущей проверки, а не уже выполненное исследование.

1. Подключить папку и объяснить, что будет архивировано при архивировании проекта.
2. Выбрать шаблон, изменить исполнителя одной роли и начать первую задачу.
3. Найти текущую цель среди истории, определить блокировку и следующего исполнителя.
4. Добавить зависимую задачу; проверить, как объяснён запрет изменения активной работы.
5. Отправить изображение агенту; объяснить разницу между сохранением и прочтением.
6. Отправить уточнение неработающему агенту и понять, что требуется для продолжения.
7. Найти последний frontend-preview и более раннее изображение другого исполнителя.
8. Пройти медленный/неопределённый save, не создав дубликат и не потеряв черновик.
9. По готовому результату понять, завершён ли запуск, есть ли review и нужно ли принять работу.
10. Создать и затем убрать тестовую группу навыков; отдельно отметить текущий пробел удаления.

Записывать: успешность без помощи, время до первого полезного действия, ошибочные
повторы, переходы не туда, обращение к CLI/оператору и понимание состояния своими
словами. Время сети, provider execution и задержку UI учитывать отдельно.
Целевые значения выбрать после baseline; численные UX-SLO в этом handoff не выдуманы.

## 9. Что ожидается от эксперта

Просьба вернуть один согласованный пакет:

1. Диагноз: 5–10 главных причин сложности с привязкой к UX-ID и экрану; где данных
   достаточно, где требуется дополнительная проверка.
2. Информационную архитектуру и глоссарий: что является проектом, библиотекой,
   исполнителем, прогоном и результатом в интерфейсе; какие слова убрать с первого уровня.
3. Основной путь от папки/идеи до первого результата и путь ежедневного контроля.
4. Wireframes ключевых наполненных экранов и состояний V01–V12; ошибки и ожидание
   считать полноценными частями дизайна.
5. Визуальное направление: типографика, интервалы, плотность, компоненты, цветовая
   семантика и rationale. Желательно сравнение двух направлений на одинаковом контенте.
6. Матрицу UI-состояний: сохранение, очередь, доставка, работа, результат, review,
   приёмка, ошибка, восстановление — с короткими примерами текста EN/RU.
7. Поэтапный backlog: быстрые улучшения, изменения navigation/flows, зависимости
   от runtime; для каждого пункта эффект, риск и проверяемые критерии.
8. План проверки с новым пользователем и перечень решений, которые действительно
   нужно принять владельцу до реализации.

Не требуется заранее соглашаться с предложенными решениями или сохранять текущие
названия вкладок. Нужна самостоятельная оценка с сохранением продуктовых гарантий.
Новый ADR и реализацию стоит делать после согласования этой экспертизы.

остаются непроверенными сценариями. Нет полного mobile/accessibility исследования,
нет статистики по новичкам и нет отдельного финального эстетического аудита.

гейтами; Linux unit CI не заменяет live qualification.

это подробная передача уже собранного опыта с проверкой документов и границы кода.
Исходники приложения, task acceptance и прежние immutable evidence не изменялись.
