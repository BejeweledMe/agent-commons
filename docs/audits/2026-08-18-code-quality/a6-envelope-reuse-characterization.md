# A6.5 — характеризация переиспользования typed envelope между fixed-point проходами

**Измеренный код:** `13a48ef7d888aa1d9e18da9fc8d9b0de472ff1ef`
(`Characterize Envelope Reuse Safety`). Этот коммит трогает только
`benchmarks/benchmark_a6_read_paths.py` и
`tests/benchmarks/test_a6_read_paths.py`; `src/` в нём побайтово равен базе
`28534c5` (`Reconcile Audit Slice Status`). Никакого production-кэша не
добавлено, не предложено и не одобрено.

**Среда:** Python 3.14.5, macOS 26.5.2 arm64, `--repeats 3`. Замер снят
2026-08-26 на локальной машине. Это evidence для решения о том, открывать ли
отдельную задачу, а не пользовательский SLO, CI-budget или сравнение с
профилями на другом железе.

## Вопрос и граница

A6.4 назвал ровно один допустимый следующий шаг: выяснить, можно ли безопасно
переиспользовать неизменяемый typed envelope одного effective event между
fixed-point проходами **внутри одного вызова `project_events()`**. Эта
страница отвечает на вопрос измерением и тестами.

Граница жёсткая и не была сдвинута ни разу:

- порядок событий, invalidation, correction-семантика, validation, применение
  события, набор issue/warning, `fixed_point_passes` и persisted JSON не
  меняются — каждый timed sample сравнивается с неинструментированным
  baseline пополю;
- кэш существует только как benchmark-локальная симуляция внутри обёрнутого
  `project_events`; ни module global, ни `functools.cache`, ни кэша на уровне
  `CommonsManager` не заводилось;
- write-path (`services/manager.py` импортирует `parse_event_envelope`
  напрямую) не задет; тест проверяет это тождеством символа;
- страница не разрешает ни одной правки в `src/`.

## Неизменяемая выборка и изоляция

Процедура A6.3/A6.4 повторена без изменений: отдельный detached worktree,
в его `.agent-commons/` один раз скопированы только canonical `events/`,
`manifests/` и `blobs/`, SQLite index и все lock/receipt-файлы — в отдельном
disposable state root. Живой checkout в замере не участвовал.

## Методика

Инструментация — отдельный контекст `_simulated_envelope_reuse`, не наслоенный
на фазовый коллектор A6.4 (иначе таймеры фаз перекрыли бы эффект). Он временно
подменяет **четыре** module globals `agent_commons.domain.projection` и
возвращает их в `finally`, в том числе при исключении:

| Обёртка | Зачем |
|---|---|
| `project_events` | создаёт и выбрасывает кэш внутри одного вызова — это и есть проверяемое утверждение о scope |
| `_project_events_once` | метка прохода (`probe`/`normal`/`final`) и сброс пер-проходных ordinal |
| `resolve_revision` | регистрирует ключ для effective payload сразу после разрешения correction |
| `parse_event_envelope` | учёт вызовов; только в serving-режиме отдаёт запомненный envelope |

Каждая обёртка начинается с ContextVar-проверки (образец `95a9de7`): вызов из
другого потока или из другого контекста немедленно идёт в оригинал.

**Ключ:** `(event_type, root_event_id, occurrence_ordinal, effective_correction_id_or_"")`,
где ordinal — 1-based номер разрешения этого root id внутри текущего прохода.
Регистрация происходит на возврате `resolve_revision`: только там известны все
три компонента. Мост `resolve_revision → parse_event_envelope` — таблица по
`id(payload)`; каждый зарегистрированный payload удерживается сильной ссылкой,
иначе переиспользованный CPython-ом адрес сфабриковал бы «попадание».
Сентинел промаха отличен от `None`, потому что целые семейства событий
законно парсятся в `None`. Исключения парсера не запоминаются никогда:
`str(exc)` попадает в текст issue и, следовательно, в digest snapshot.

**Три timed-плеча, чередующиеся внутри каждого repeat** (`reuse_baseline` без
обёрток → `account` → `shadow`), чтобы дрейф машины двигал все три вместе:

- `account` — учёт без подмены: оригинальный парсер вызывается на каждом
  вызове, запомненное значение только сравнивается с ним. Это плечо строго
  медленнее измеряемого кода и не способно изменить результат;
- `shadow` — serving-плечо, которое действительно отдаёт запомненный envelope;
- экономия публикуется **только** как медиана парных разностей
  `account − shadow` внутри одного repeat.

**Неизмеряемые по времени плечи:** отдельный purity-прогон digest-ит вход
каждого парса (слишком дорого, чтобы оставлять внутри timed-плеча, поэтому его
собственные секунды не публикуются) и изолированный цикл парсинга по
записанной последовательности `(event_type, payload)` вне replay.

**Что сравнивается.** Расширенная integrity-запись содержит digest snapshot,
отсортированные `known_event_ids` и `known_manifest_ids`, applied ids в
порядке вставки, полное отображение `effective_event_revisions`,
`fixed_point_passes`, полные `replay_metrics`, каждый issue как
`(code, severity, message, event_ids)` в исходном порядке и сырую
последовательность warnings. Каждый sample сравнивается с baseline **пополю в
процессе**; в JSON сохраняются `integrity_sha256` каждого sample и один полный
`baseline_integrity` — так файл остаётся читаемым, но проверка от этого не
слабеет: несовпадение любого поля роняет прогон до записи результата.

Это не декоративная проверка. Сломанный кэш не падает: `KeyError` внутри
apply-loop превращается в обычный `domain_validation_rejected`, и прогон
«успешен». Негативный контроль показывает это буквально: serving-плечо с
ключом только по root id на фикстуре `duplicate_root_divergent` тихо теряет
вторую задачу, а `snapshot.issues` остаётся пустым — ловит это исключительно
сравнение с baseline. Стабильность счётчиков между repeats тоже принудительна:
дрейф учёта роняет прогон, а не усредняется.

## Воспроизведение

Из корня detached worktree, где `<snapshot-root>` содержит read-only canonical
деревья, а `<state-root>` — новый disposable каталог:

```text
env -u AGENT_COMMONS_STATE_BASE -u AGENT_COMMONS_SESSION_ID \
  -u AGENT_COMMONS_SESSION_NONCE AGENT_COMMONS_STATE_ROOT=<state-root> \
  uv run --locked python benchmarks/benchmark_a6_read_paths.py \
  --components-only --repo <snapshot-root> --state-root <state-root> --repeats 3
```

Профиль получил схему `agent_commons.a6_read_path_profile.v2` и секцию
`envelope_reuse_profile`; `--no-envelope-reuse` её отключает.

## Синтетическая проверка (400 событий, 2 прохода)

Синтетический прогон характеризует семантику, а не стоимость: 800 вызовов
парсера, 400 повторов, из них **8 typed и 392 `None`** — разбиение обязано
стоять в одном предложении с любой долей, иначе «50% повторов» читается как
50% избегаемой полезной работы. Медиана парной экономии — 0.012728 с
(samples 0.012820 / 0.012728 / 0.012355). Фаза парсинга там стоит 34.4 мкс на
вызов против 322.3 мкс на реальном ledger, поэтому ни одно стоимостное число
синтетики в выводы не входит.

## Что именно доказывает ключ

Все сценарии закреплены тестами в режиме симуляции: инструментация всегда
вызывает оригинальный парсер, поэтому несостоятельность ключа проявляется не
испорченным результатом, а положительным счётчиком.

- **Одного root id недостаточно.** Apply-loop не дедуплицирует повторённый
  root event id: обе записи парсятся и применяются. На фикстуре с расходящимися
  payload-ами ключ только по root id даёт 2 расхождения (17 первых встреч,
  19 повторов) против 0 расхождений с occurrence-ordinal (18 / 18). Verbatim-
  вариант той же фикстуры даёт 0 расхождений в обеих стратегиях и оставлен
  намеренно: он убивает мутацию «пропустить сравнение envelope».
- **Ordinal вызова парсера тоже несостоятелен.** На трёхпроходной фикстуре
  проходы дают 20 / 20 / 19 парсов; последовательность ключей финального
  прохода расходится с normal с индекса 15, потому что в середине выпадает
  forced-stale `task.accepted`. Ключ по номеру вызова с этого места молча
  выдавал бы чужой envelope.
- **Correction-голова нужна.** Тройка «валидная / перекрытая / погашенная
  correction» даёт для одного и того же `(root, ordinal)` три разных
  правильных ответа: `Original`, `Corrected once`, `Corrected twice` — и
  различает их только третий компонент ключа (`""`, `evt…0201`, `evt…0202`).
- **Кэш маскирует падения, если ключ слаб.** На фикстуре с повторённым root id
  и битым вторым payload-ом парсер падает 2 раза в обеих стратегиях, но
  счётчик «падение замаскировано кэшем» равен 0 для occurrence-ключа и 2 для
  ключа только по root id.
- **События, отброшенные до парсера, не вносят ничего.** Структурно
  заблокированная correction, конфликт нескольких голов, malformed payload,
  отклонённый на `validate_payload`, — ни ключа, ни вызова парсера; порядок
  issue (сначала resolution, потом apply-loop) закреплён отдельно.
- **Изоляция вызова.** Два вызова с одинаковой последовательностью ключей и
  разными payload-ами: 2 вызова `project_events`, 34 первых встречи, 34
  повтора, 0 расхождений. Убивающая пара намеренная: одного `divergences == 0`
  мало — его удовлетворила бы инструментация, которая вообще ничего не
  кэширует, поэтому число первых встреч закреплено тоже. Контроль, в котором
  кэш переживает вызов, даёт 17 первых встреч и 2 расхождения.
- **Изоляция потока.** Пока инструментированный контекст replay-ит одну
  историю, посторонний поток гоняет `project_events` другой: счётчики
  контекста ровно `probe 17 / normal 17 / final 0`, 17 первых встреч, 17
  повторов, один вызов.
- **Вход вызывающего не меняется.** Хэш до/после, сравнение с deepcopy,
  тождество объектов и отсутствие ключей с `_` проверены на трёхпроходной и
  correction-фикстурах.

## Ограничения и честные оговорки

1. **В реальном ledger нет ни одной correction.** `corrections_indexed=0` на
   всём snapshot: каждый correction-путь охарактеризован **только**
   синтетическими фикстурами. Утверждение «ключ корректен на реальной истории»
   не покрывает correction-семантику.
2. **Доля повторов зависит от истории.** Более раннее состояние живого ledger
   (1 618 событий) реплеилось в три прохода с долей повторов 66.4%; этот
   замороженный snapshot из 1 619 событий реплеится в два прохода с 50.0%.
   66.4% нельзя цитировать как текущее число, а число проходов — как свойство
   репозитория.
3. **Абсолютные секунды несопоставимы со страницами A6.3/A6.4.** На этом
   прогоне медиана `project_events` — 2.888003 с против 2.097866 с у A6.4
   (≈1.4×) при snapshot всего на 20 событий больше; `sync()` вырос вдвое.
   Сравнивать между страницами можно только отношения внутри одного прогона.
4. **Tier 2 не может нести часть фикстур.** Дублированный root event id
   схлопывается в `{event_id}.json`, а malformed payload отвергается
   verified-reader-ом до replay. Обе проверки живут только на прямых вызовах
   `project_events()`.
5. **Экономия serving-плеча — верхняя граница.** Оно отдаёт кэш, не платя ни
   за построение ключа, ни за время жизни, ни за вытеснение; production-кэш
   платит.
6. **Identity-охрана вероятностна.** Счётчик `identity_mismatches` —
   защитный: удержание payload-ов делает коллизию `id()` недостижимой, поэтому
   его ноль свидетельствует о целости реестра, но не является доказательством.
7. **Purity доказана только для измеренных историй.** Ни один прогон не
   доказывает чистоту ключа для историй, которых здесь не было.
8. **Стоимость парсинга включает двойную валидацию A5.2.** Семейный парсер
   `task_review_envelopes.py:296-303` повторно гоняет `validate_payload` и
   `Draft202012Validator` внутри себя. Починка двойной валидации —
   **неизмеренная** альтернатива, которая может как конкурировать с
   переиспользованием, так и складываться с ним; эта страница её не мерила.
9. **`resolve_revision` не затрагивается** идеей вовсе (0.187611 с на 3 230
   вызовов в этом прогоне).
10. **Медианы разных плеч и фаз нельзя складывать** — они получены из разных
    samples. Ни одно число здесь не является пользовательской задержкой, SLO
    или CI-budget.

## Зафиксированные расхождения команды

- **Порядок компонентов ключа и третий компонент.** Меморандумы разошлись в
  порядке `(… correction_id, ordinal)` против `(… ordinal, correction_id)` и в
  том, писать ли в третий компонент `""` или root id при отсутствии
  correction. Обе пары различают ровно одинаковые множества входов;
  реализовано `(event_type, root_event_id, occurrence_ordinal, correction_id)`
  с пустой строкой, и тесты закрепляют именно этот вид.
- **Serving против чистой симуляции.** Разрешено fail-closed: все тесты
  пришпилены в режиме симуляции (никогда не подменяют), а serving-плечо
  допущено в benchmark только под пополевой integrity-проверкой каждого sample
  и негативным контролем. Путь сброса плеча при первом расхождении реализован,
  но ни разу не выполнялся.
- **Кэширование падений с точной идентичностью исключения** отвергнуто
  fail-closed: падения не запоминаются никогда.
- **Необходимость correction-головы в ключе.** Внутри одного вызова голова —
  функция root id (несколько голов дают конфликт и событие вообще не
  парсится), поэтому строго различающей она там не является. Она оставлена в
  ключе как fail-closed охрана: в production-коде нет ничего, что заставляло
  бы такой кэш умереть вместе с вызовом. Обе половины утверждения
  зафиксированы намеренно.
- **Отклонение автора страницы.** Фикстура `duplicate_root_verbatim` даёт
  дополнительный issue `lifecycle_rejected` (повторное `task.created` для той
  же задачи), которого в исходном плане не было. Строка оставлена как
  `divergences == 0`: её ценность — убивать мутацию «не сравнивать envelope»,
  а не демонстрировать чистую историю.

## Go/no-go

**Go** — на открытие **отдельной** задачи проектирования production-кэша.
Узкий вывод, который эта страница поддерживает: переиспользование typed
envelope выглядит корректным внутри одного вызова `project_events()` при ключе
`(event_type, root_event_id, occurrence_ordinal, effective_correction_id_or_"")`,
при не-`None` сентинеле промаха, при обращении к кэшу строго после
resolution-охран и `validate_payload` и при жизни кэша не дольше одного вызова.
Ключ только по root id и ключ по номеру вызова парсера опровергнуты
конкретными контрпримерами.

**No-go** — на любую правку `src/` по этой странице. Она не является ни
одобрением оптимизации, ни SLO, ни утверждением о пользовательской задержке.
Согласно `r-status-reconciliation.md` («A6 evidence boundary»), следующая
кодовая правка A6 требует собственной, отдельно взятой задачи.

Что такой задаче ещё предстоит доказать, прежде чем появится код:

1. **Дельту памяти настоящего кэша** — здесь она не измерена: пики reuse-плечей
   раздуты инструментацией.
2. **Структурные тесты на scope**: сегодня «один вызов» ничем в коде не
   удерживается; production-версия обязана нести охрану и тест, который падает
   от кэша, пережившего вызов.
3. **Измеренную альтернативу** — починку двойной валидации семейства A5.2,
   чтобы выбор между двумя работами делался по числам, а не по очерёдности.
4. **Correction-несущую реальную историю** либо явно обоснованную
   синтетическую замену: на текущем ledger correction-путей нет вовсе.
5. **Повторный замер на тогдашнем ledger**: число проходов и доля повторов
   зависят от истории и уже менялись между двумя измерениями этой команды.
