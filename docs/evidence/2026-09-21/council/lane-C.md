# Lane C — продуктовая стратегия: что защищает дифференциатор Agent Commons, а что его размывает

## 1. Диагноз

Дифференциатор Agent Commons — не доска и не трекер задач, а протокол доверия между эфемерными сессиями провайдеров: неизменяемый файловый леджер (`src/agent_commons/domain`) плюс цикл `Run → независимый Review → человеческое Acceptance`, где «согласие моделей — не доказательство» (`docs/PRODUCT.md`, строки 45–56, 84–95). Это явно сформулировано как то, чем продукт **не** является: «not an autonomous agent swarm... not a replacement for Git, CI or issue trackers» (`docs/PRODUCT.md:97-103`). То есть сам PRODUCT.md уже определяет границу: инструмент координации и доказуемости, а не трекер и не автономный рой. Это я подтверждаю чтением документа, не выводом.

По жалобе (1) — «выглядит как Streamlit-поделка» — я проверил структуру, не рендер: `frontend/work/src/main.tsx` — 1859 строк одним файлом, `styles.css` — 1299 строк, при этом уже существует ~29 вынесенных компонентов (`DecisionCard.tsx`, `TaskGraph.tsx`, `ProjectBoard.tsx` и т.д.) и токенная система по брифу. Это симптом монолитного файла-роутера и рукописного CSS без компонентной библиотеки — правдоподобная техническая причина ощущения «на коленке», но я **не открывал приложение и не видел скриншотов**, поэтому не подтверждаю визуальную оценку напрямую. План консолидации уже видит эту боль и адресует её волной 4 (WP-18 первый запуск, WP-19 пустые/сбойные состояния доски, WP-22 внимание, WP-23 тексты отказов, WP-25 a11y-gate) — то есть инстинкт (a) владельца **уже частично в работе**, не новая идея.

По (2) — пивот в обёртку над Linear/Jira — этого пункта **нет** в `docs/plans/2026-09-18-consolidation-and-wave-4-plan.md` вообще; это новая, незапланированная ось работы, конкурирующая за то же внимание одного владельца + AI-исполнителей, что и волна 4.

По (3) — «переиспользовать существующее» — план уже переиспользует: провайдерские CLI как рантайм (ADR 0004), a11y и токены — стандартные практики, не custom-фреймворк. Риск — трактовать инстинкт (3) как разрешение притащить чужой фреймворк оркестрации (LangGraph, Hermes) туда, где уже есть **более строгий** примитив — неизменяемый леджер с ревизиями, — и тем самым ослабить именно то, что отличает продукт.

## 2. Варианты

**A. Только волна 4, без нового скоупа.** Закончить консолидацию и WP-18…WP-25 как запланировано. Стоимость: план уже оценён (недели, конкретные пакеты Opus/Astra); риск низкий — работа уже расписана и частично принята (чек-лист плана). Ничего не теряется, дифференциатор не трогается.

**B. Пивот трекера в обёртку над Linear/Jira.** Задачи живут в Linear/Jira, Agent Commons хранит мету (исполнитель, зависимости, связи) и рисует граф поверх чужих данных. Стоимость: минимум двусторонняя синхронизация состояний + маппинг «review/acceptance» (которых в Linear/Jira нет как понятия) на их статусы — это не адаптер на неделю, а постоянно поддерживаемая интеграция против чужого API, который сам меняется (Linear уже выпускает собственный агентский слой — Developer Preview «Linear for Agents API» и агенты внутри рабочего пространства с «Loops»; Jira с лета 2026 сам маршрутизирует тикеты кодинг-агентам через Jira Coding Agent). Риск: конкурировать с дорожными картами Linear и Atlassian на их территории — заведомо проигрышная гонка для одного владельца. Теряется: собственная семантика review/acceptance (либо дублируется вне Linear/Jira, либо выхолащивается до их статусов).

**C. Гибрид — экспорт/просмотр, не источник истины.** Леджер остаётся каноническим; опционально — read-only или push-only синхронизация в GitHub Issues/Projects (тот же экосистемный слой, что уже используется для кода) для человека, который **уже живёт** в трекере. Не начинается, пока нет второго реального пользователя с такой потребностью. Стоимость малая, потому что не строится сейчас вообще — это решение, а не код.

**D. Точечное заимствование паттернов оркестрации без смены ядра.** Смотрим на LangGraph (durable execution, human-in-the-loop чекпоинты, потоковые режимы) и на Hermes Agent (профили как изолированные агенты со своей памятью и конфигом — близко к текущей модели агента Agent Commons) не как на библиотеки для установки, а как на источник идей для уже существующего брокера (ADR 0004). Стоимость: 1 короткий спайк на чтение и сравнение, без изменения кода леджера.

## 3. Рекомендация

Вариант A + D, с B явно поставленным на паузу (см. открытые вопросы). Первые три шага:

1. Довести текущий поток C (консолидация) и волну 3 до merge без добавления нового скоупа — чек-лист плана уже показывает, что это почти сделано (C1–C4, C7 закрыты, PR и мердж — следующие шаги).
2. «Премиальность» атаковать дешёво и без риска для бэкенда: в рамках WP-18/19/22/23/25 заменить рукописный CSS в `styles.css`/`main.tsx` на готовую компонентную библиотеку (см. раздел 4) — это прямой ответ на инстинкт (a) *и* инстинкт (c) одновременно, без изменения протокола review/acceptance.
3. Зафиксировать решение по Linear/Jira как явно отложенное: короткая запись в `docs/plans/` или decision-запись в леджере с условием пересмотра (см. открытые вопросы), чтобы идея не тянула внимание исподволь на каждой сессии.

## 4. Что переиспользовать

- **Компонентная UI-библиотека (например, Radix Primitives + shadcn/ui-подход, либо аналог) поверх существующего Tailwind/токенной системы** — заменяет рукописные 1299 строк CSS и часть вёрстки в `main.tsx`; отвечает на «не похоже на премиальный сервис» дешевле, чем полный редизайн.
- **Провайдерские CLI как рантайм (уже реализовано, ADR 0004)** — это и есть правильная точка переиспользования вместо оркестрационного фреймворка: продукт уже не пишет «нейросеть на NumPy» в части исполнения агентов.
- **Идеи из Hermes Agent** (агент = профиль с изолированной памятью/конфигом, «визуальные орг-чарты» делегирования) — как референс для модели «агент в проекте» и для карты `TaskGraph.tsx`, а не как зависимость.
- **GitHub Issues/Projects**, а не Linear/Jira, — если/когда внешняя синхронизация понадобится: тот же экосистемный слой, что уже используется для кода, меньше поверхность интеграции, чем у двух проприетарных трекеров сразу.
- **LangGraph — только как источник паттернов** (checkpoint/resume, потоковые режимы), не как замена леджера: его state-граф не даёт неизменяемости и revision-aware ревью, которые уже есть и сильнее нужны здесь.

## 5. Чего не делать

- Не переписывать трекер в обёртку над Linear/Jira до появления второго реального пользователя, который уже живёт в одном из них; сейчас пользователь один — сам владелец, и решение принимается за гипотетического человека.
- Не устанавливать LangGraph, AutoGen, Hermes или OpenClaw как исполняющий слой вместо текущего брокера — это заменило бы неизменяемый append-only леджер на чужую модель состояния и разрушило бы ревизионную семантику review/acceptance, которая и есть продукт.
- Не переводить «премиальность» в полный редизайн, трогающий бэкенд-контракты (`docs/FRONTEND_CONTRACT.md`) — ограничить изменение слоем компонентов/токенов.
- Не давать инстинкту «переиспользовать» стать разрешением на автономный рой агентов — это прямо противоречит заявленному «not an autonomous agent swarm» в PRODUCT.md.

## 6. Открытые вопросы владельцу

1. **Личный инструмент, open-source проект или SaaS?** От ответа зависит, сколько вкладывать в «премиальность»: (а) личный инструмент — polish ограничивается удобством для одного человека, a11y-gate и онбординг для чужих людей не критичны; (б) open-source для других связок владелец+агенты — нужна хорошая документация и install-опыт, не корпоративный UI; (в) SaaS — тогда нужны совсем другие вещи (аутентификация, мультитенантность, хостинг, security review), которых сейчас нет в плане вообще.
2. **Владелец сам уже живёт в Linear или Jira?** (а) да — тогда обёртка может быть личной пользой уже сейчас, но это меняет её оценку с «гипотетический пользователь» на «пилот для себя»; (б) нет — тогда обёртка строится для человека, которого пока не существует, и стоит явно отложить её до появления такого пользователя.
3. **Какое условие возвращает вопрос про Linear/Jira на стол?** (а) появление второго реального пользователя с такой трекерной привычкой; (б) конкретный болевой пункт в собственном трекере, который вырос настолько, что дешевле обернуть чужой; (в) фиксированный таймбокс (например, «вернуться к вопросу после релиза L1/R2»). Без выбранного триггера идея рискует возвращаться на каждой сессии без нового факта.
