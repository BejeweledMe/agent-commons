# Полоса D — что код уже есть и во что обойдётся каждый разворот

Ревизия осмотра: `main`, `5153a56` (в брифе указан `c68cee1` — ветка ушла вперёд).
Репозиторий не менялся.

## 1. Диагноз

**Соотношение «хром / домен» во фронтенде.** `frontend/work/src` — 12 845 строк
(TS/TSX/CSS, 82 файла). Из них домен: `api.ts` 2 284, `contracts.ts` 465,
~20 модулей состояния (`boardState`, `trackerState`, `launchIntentState`,
`mutationRegistry`, `taskPresentation`…). Визуальный слой — 1 501 строка CSS,
232 класса и 31 компонент, причём крупнейший из них `TrackerSection.tsx` — 378
строк. То есть «UI-библиотеки» нет вовсе: есть токены и плоский CSS.
Токен-система реальная: 47 переменных в `:root` (шкала отступов 4–48, шрифта
12–24, семантические цвета), и она закреплена тестами `style-tokens.test.mjs`
(ratchet «0 сырых hex вне :root») и `contrast.test.mjs` (WCAG считается из
значений `:root`). Это не Streamlit-уровень — это недоведённый дизайн-язык.

**Где на самом деле болит.** Я посмотрел свежие кадры догфудинга
(`docs/evidence/2026-09-21/blizhe-dogfooding/`, 27 файлов, не закоммичены).
`V08-inspector-failed-EN.jpg` — инспектор задачи это ~4 000 px одной колонки,
все секции раскрыты, `task.5Z93Z3BN834V2ZYXF53228KG46` и
`evt.03M3292KF4Q5O3QW640Y2G1PE6` набраны основным весом, «Expected outcome» —
сплошная стена текста, правый край обрезан на viewport 1042. `V02-team-final-EN`
— в сайдбаре две несвязанные навигации (проекты и разделы), кнопка «New project»
переносится на две строки, и над доской два абзаца документации подряд
(«Departments coexist on one board; runs from different departments queue through
the broker (one writer per checkout)»). Ощущение «хобби-проекта» даёт не палитра,
а **отсутствие иерархии и прогрессивного раскрытия**: продукт печатает всё, что
знает бэкенд.

**И это не главное.** `docs/handoffs/2026-09-21-blizhe-dogfooding-feedback.md`:
ни один настоящий прогон BASE не дошёл до работы агента (P0 UX-19 — MCP
snapshot падает на вложенных worktree, `scoped reviewer files must be regular`;
причина не видна в UI, владелец ушёл в CLI). Плюс из активного плана:
warm `task_create` — **33 с** на 3 206 событиях, 62–64 % — двойная валидация
леджера (WP-20). Сервис, который сохраняет задачу 33 секунды и не объясняет
отказ прогона, будет выглядеть самодельным при любой палитре.

**Связанность трекера с леджером — высокая и осмысленная.** Событийный словарь
~35 типов (`task.created/revised/accepted`, `review.requested/completed`,
`delegation.*`, `decision.*`, `event.invalidated/corrected`). `domain/projection.py`
— 1 268 строк, `lifecycle.py` — 936, `validation.py` — 676. Задача несёт CAS
(`expected_revision` в каждой мутации), привязку приёмки к ревизии артефакта и
каскад устаревания (`_mark_bound_evidence_stale`). На `task.created`/
`accept_task`/`expected_revision` ссылается 61 тестовый файл; всего Python —
206 файлов, 1 904 тест-функции, из них `tests/ui` 65 файлов.

**Исполнение.** `runtime/broker.py` — 273 строки: зарезервировать → запустить →
наблюдать → терминально классифицировать **один процесс провайдера**.
`attempts.py` (1 175) — уже durable-стор: `reserve/transition/finish/reconcile`,
состояния `reserved…needs_operator`, бюджет, эксклюзия писателя по checkout,
идемпотентность по `request_id` + `semantic_sha256`.
`services/delegation_runtime.py` — 1 972 строки, 50 методов, но это **клей**:
~14 методов — привязка context pack / design package, ~10 — auth/qualification/
canary; сам `run()` — 322 строки.

Чего **не** проверял: реальную скорость записи (беру цифру из плана), поведение
Radix/shadcn под текущим CSP, и API Jira (смотрел только Linear).

## 2. Варианты

**A. Полировка без переписывания.** Свой набор из ~10 примитивов (Button, Card,
Field, Dialog, Tabs, Disclosure, Badge, Table, EmptyState, Toolbar) поверх
существующих токенов + иерархия инспектора + добивание P0 прогона и WP-23.
**5–7 недель.** Риск низкий. Теряем: ничего, кроме соблазна «нового стека».

**B. Обёртка над Linear/Jira.** Адаптерами станут `services/tasks.py`,
`domain/task_projection.py`, `task_edits.py`, `task_review_envelopes.py`,
`ui/tracker_reads.py` (485) + `tracker_dtos`/`tracker_routes`/`task_edit_routes`,
и `execution_plan` (домен 15 821 байт + сервис 685 строк). Ломаются инварианты:
CAS по ревизии, `event.invalidated`/`event.corrected` (в Linear есть история
правок, но нет аннулирования как факта), каскад устаревания доказательств,
привязка приёмки к ревизии и **local-first** — у Linear нет офлайн-записи, есть
2 500 запросов/час и 250 000 очков сложности/час на ключ. Плюс в угрозной модели
появляется второй писатель, которым вы не владеете. **10–16 недель** на полный
разворот; переписывается 61 тест-файл и заметная часть `tests/ui`.
Дешёвый честный вариант — **односторонняя витрина**: леджер остаётся истиной,
в Linear уходят issue + связи как проекция, обратно ничего. **3–5 недель**,
один модуль, ноль изменённых инвариантов.

**C. LangGraph как рантайм vs заимствование его приёмов.** *Адопция:*
LangGraph исполняет узлы **внутри процесса** с checkpointer'ом и `thread_id`;
Commons запускает **внешние CLI провайдеров** под редукцией политик, argv-gate и
идемпотентностью. Сохранить придётся всё: `subprocess_runner`, `exec_gate`,
`policy`, `attempts`, `provider_auth`, `canary`, `preflight` — сверху ляжет слой,
который решает «что дальше». **6–10 недель**, новое дерево зависимостей и
пере-вывод угрозной модели (последовательность начинает выбирать фреймворк).
Отдача близка к нулю: тип узла один, а связка «прогон → независимая проверка →
приёмка» — это переход в леджере с участием человека, а не ребро графа.
*Заимствование:* типизированное состояние — уже есть (frozen dataclass + StrEnum),
durable checkpoint — уже есть (`AttemptStore` + `reconcile()`), interrupt — уже
есть (`needs_operator` / `delegation.input_needed`). Реально не хватает трёх
вещей: (1) **объявленного именованного графа шагов** прогон→проверка→приёмка,
чтобы UI показывал «где мы», не угадывая это в `execution_plan.py`;
(2) **идентичности возобновления** в духе `thread_id`, видимой оператору;
(3) **типизированной полезной нагрузки прерывания** — сегодня «нужен человек»
не несёт структурного «что именно от вас нужно», и догфудинг это ровно и
показал. **1,5–3 недели, ноль новых зависимостей.** Отдача несопоставимо выше.

**D. Переезд на Radix/shadcn.** Это не замена зависимости: Radix позиционирует
всплывающие слои инлайновыми `style`, а `FRONTEND_CONTRACT.md` запрещает inline
style (в CSP нет `style-src-attr`), плюс ratchet «0 hex вне :root», точный список
47 токенов и правило одного закоммиченного бандла. **6–9 недель** и потеря
доказанных сегодня гарантий контраста. *(Поведение Radix под CSP не проверял —
спекуляция.)*

## 3. Рекомендация

**Вариант A + заимствование приёмов (C-lite).** Первые три шага:

1. **Довести один настоящий прогон до конца** (UX-19 + UX-10): вложенные
   worktree в MCP snapshot, обнаружение отказа до расхода попытки, и точная
   безопасная диагностика в карточке прогона. Исполнитель Codex, независимая
   проверка Claude. 2–3 недели.
2. **Пакет «иерархия»**: примитивы на текущих токенах + прогрессивное раскрытие
   инспектора + вынос абзацев-инструкций в одно раскрытие/пустое состояние +
   токены радиуса, тени, движения и фокуса с тем же ratchet-тестом. Исполнитель
   Opus, механические замены — Grok. 2–3 недели.
3. **Типизированное прерывание и именованный граф шагов** в
   `delegation_runtime.py`: `InterruptReason` с кодом, человеческой причиной и
   одним действием, и явный `run → review → acceptance` вместо эвристик.
   1,5–3 недели. Сюда же — `.claude/agents` (сейчас каталога нет, проверял):
   6 пресетов 1:1 к профилям брокера, ~2 дня, нулевая архитектурная цена.

## 4. Что переиспользовать

- **Приёмы LangGraph** (checkpoint/interrupt/typed state) — не библиотеку.
  Заменяют: самодельные эвристики готовности в `execution_plan.py`.
- **Linear — только как витрину** через GraphQL API и webhooks, если владельцу
  нужен внешний вид графа. Заменяет: ничего в леджере.
- **React Flow + dagre** уже стоят — автораскладка и граф задач бесплатны.
- **Свой набор примитивов**, а не shadcn: сохраняет CSP, ratchet и a11y-тесты.
- **`.claude/agents`** как пресеты вместо ручного выбора исполнителя.

## 5. Чего не делать

Не переносить истину задач во внешний трекер. Не ставить LangGraph рантаймом.
Не декомпозировать `main.tsx` (1 631-строчный `WorkApp`, 38 `useState`) отдельным
проектом: 39 `assert.match` по **исходному тексту** `main.tsx`/`styles.css` в
`work-shell.test.mjs` и `instrumentation.test.mjs` делают рефакторинг платным и
невидимым — разбирать только попутно под фичами. Не начинать косметику раньше
шага 1. Не вводить светлую тему.

### Приложение: дёшево vs дорого

**Пять дешёвых (итого ~2–3 недели):** (1) иерархия и прогрессивное раскрытие
инспектора — 3–5 дней; (2) абзацы-инструкции на доске → одно раскрытие и
осмысленные пустые состояния — 2–3 дня; (3) токены радиуса/тени/движения/фокуса
(сейчас 11 разных `border-radius`, **один** `transition` на 1 501 строку CSS,
`focus-visible` в 13 местах) — 3–4 дня; (4) одна навигация в сайдбаре вместо двух
+ кнопка, не переносящаяся на две строки — 2–3 дня; (5) сырые ULID в теле текста
→ тихий моноширинный стиль с копированием и правило в контракте — 1–2 дня.

**Три дорогих:** (1) 33 с на `task_create` — инкрементальная валидация леджера
без ослабления инвариантов, 2–4 недели с независимой проверкой; (2) сквозной
путь прогона и каталог типизированных причин отказа, 2–3 недели; (3) разбор
монолита `main.tsx` вместе с переписыванием текстовых assert'ов, 3–4 недели и
ноль видимой пользы — только попутно.
