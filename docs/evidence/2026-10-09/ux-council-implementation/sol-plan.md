# Sol: план одной frontend-волны после аудита 9 октября

Это предложение GPT-6.1 Sol для обсуждения с Sonnet 5.5 и интеграции организатором. Прочитаны README, первые ответы Sol/Sonnet/Grok, рецензии Sol/Sonnet и общее дополнение; выборочно проверены замороженные исходники `/private/tmp/oct09-design-council/source`. Браузер, записи и новая эксплуатационная проверка не выполнялись. Это не новый аудит и не утверждение о согласии всех трёх участников. У Grok есть первый ответ; новый раунд ограничен квотой до 13 октября, отсутствующее согласие ему не приписывается.

## Решение для обсуждения

Одна волна «читаемая карта и самостоятельные действия»: исправить вход в наём и выдачу задачи, обзорный/рабочий масштаб, видимый keyboard-фокус, понятные области сохранения и честные статусы. UX-01–19 входят в один перечень приёмки; дешёвые изменения языка и пустых состояний выполняются рядом с основными, без отдельной косметической кампании. Основной продукт остаётся инструментом технического пользователя desktop/Mac.

Оба текущих движка карт сохраняются: React Flow у агентов и SVG MapCanvas у задач. Переписывать их в этой волне не требуется. Меняется пользовательская работа с масштабом и контентом; графовые факты, запуск, права и DTO не переопределяются.

## Неизменяемые пользовательские ограничения

1. Карта — центр рабочих вкладок. Две карты остаются рядом, боковые проекты/главный чат сохраняют свой смысл.
2. Деталь задачи — большое временное native dialog поверх карты, ×/Esc, без нового sidebar и без уменьшения геометрии карты. Закрытие по backdrop не вводится. Форма создания может использовать `size="medium"`.
3. Профессия/специализация — главный заголовок агента; различающее назначение — заметная вторая строка. Служебное имя не возвращается в главный заголовок.
4. Дерево руководителей строится только по сохранённым supervisor-связям. Владелец означает принадлежность проекту, creator — происхождение, communication — разрешённую связь. Нельзя назначить руководителя по названию роли или перетаскиванию карточки.
5. UNKNOWN доступности сохраняется неизвестностью. Сообщение можно записать без активного получателя, если существующие проверки записи это допускают. Запись сообщения, доставка и ответ показываются как разные события.
6. Только записанная приёмка зелёная. Настройка workspace, квалификация профиля, успех прогона и принятое человеком выполнение не объединяются.
7. Канонические значения не переводятся и не удаляются. Человеческое объяснение можно поставить первым; точный enum остаётся в технических подробностях.
8. После открытия/закрытия окна, обычного refresh и возврата во вкладку не сбрасываются пользовательская камера, выбранная задача и локальные черновики.

## Как реализовать масштаб без дорогой переписки

Самое рискованное место — semantic zoom. Простое скрытие строк оставит прежний 5px текст и не выполнит UX-01. Нужно проверить именно экранный размер, а не CSS-значение до трансформации.

- Добавить в MapCanvas способ передать дочерним узлам вычисленные `zoom`, frame и effective viewport, например render-function children. React Flow передаёт текущий zoom через существующий viewport/session либо свой supported hook. Новая зависимость не нужна.
- Компактный контент скрывает role/provider/run/metadata и ряд действий. Короткая подпись/иконка состояния получают классы по нескольким диапазонам zoom; stylesheet увеличивает map-unit шрифт так, чтобы при исходных 33/38/46% видимые короткие метки были около 11–12px. Inline style/CSS-variable attributes запрещены CSP. SVG атрибуты позиции допустимы, цвета только токены/classes.
- Неизменная геометрия foreignObject/React Flow node не вызывает re-layout, не перезаписывает сохранённые позиции и не рисует другие отношения. Верхняя строка агентской compact-карточки остаётся профессией, вторая — назначением.
- При очень низком fit, где даже краткие метки не умещаются в узле, не претендовать на читаемость всех узлов: состояние+короткая метка в обзоре, выбранный элемент читается в немасштабируемой полосе, поиск/список и «Рабочий масштаб» решают подробное действие. «Рабочий масштаб» должен сохранять выбранный узел в центре и оставлять его доступным клавиатурой.
- Полоса выбранного агента/задачи принадлежит верхнему toolbar карты, не является sidebar. Не открывает новый persistent inspector. Для задач достаточно имени/state/перехода в уже существующий modal; для агента профессия/назначение и три действия.
- Единая reveal-функция в mapViewport принимает viewport, node rectangle, frame, content, screen-pixel margin. Если node больше рамки, центрирует его и оставляет фокусируемую основную часть видимой вместо бесконечного ping-pong. Камера не меняется от обычного focus-return или data refresh.

## Последовательность внутри единой волны

1. **Сначала поведение:** hire-first, picker задачи, reveal viewport, no-op/dirty selectors. Эти изменения дают измеримые рабочие результаты и тестируются до сборки ассетов.
2. **Затем карточки и масштаб:** компактный контент, working zoom, selected action strip, различимость профессии/назначения, прямые/вторичные действия и hints. Изменение карточки сохраняет высоту layout. Не смешивать его с перенастройкой Dagre gaps.
3. **Затем редакторы/навигация:** embedded composer, library modal возврат, textarea, clear save scope. Меняются размеры/композиция окон, а не правила подтверждения записи.
4. **Затем презентация фактов и строки:** task now/history/stale, workspace/profile, chat help, brief/criteria, locale/empty. Парные RU/EN проходят registry validation.
5. **Один интегратор ассетов:** после согласования всех исходных изменений выполняет предусмотренный CONTRIBUTING rebuild path, обновляет Work/Gallery dist и exact manifest. Никаких конкурентных билдов.

Файлы реализации: `frontend/work/src/main.tsx`; `components/{ProjectBoard,MapCanvas,TaskGraph,TaskHierarchy,AgentSettings,TaskComposer,TaskInspector,DecisionCard,ServiceLibrarySection,ConversationPanel,OutputsPanel,Icon,Modal}.tsx`; `mapViewport.ts`, `agentSettings.ts`, Work/Gallery locale entrypoints и shared preference helper; ограниченные изменения `board.css`, `taskGraph.css`, `conversation.css`, `styles.css` и парных i18n. Не каждый файл обязан меняться: переиспользовать существующую композицию, не добавлять общий framework для этой волны.

## Проверка и доказательство, которое должен вернуть builder

`make check` — обязательный зелёный контракт репозитория после всей волны. До него адресные проверки существующих graph, agent-settings, conversations, service-library, task-inspector, work-shell, style/i18n suites. Не добавлять тесты, которые только ищут новую строку обработчика; наиболее полезны следующие:

1. **Viewport arithmetic:** hidden rectangle reveal в каждом направлении, уже видимый rectangle unchanged, margin при различных zoom, oversized node, invalid numeric guard, resize сохраняет центр/zoom. Это проверяет математику, однако не заменяет живой SVG focus test.
2. **Write safety:** config/no-op/method-no-op и version fork только при реальных изменениях; unrelated draft остаётся dirty после сохранения другой области; reload keeps; uncertain retry same key; confirmed refresh no replay.
3. **Action intent:** task-picker select формирует ровно navigation/preparation, не POST; первоначальное открытие найма/инструкций тоже read-only. PendingLaunch lock сохраняется.
4. **Conversation:** unknown+непустой новый thread по-прежнему canSubmit; empty/64KB/pending-upload/read-only boundaries; recorded receipt и reply разные. Добавить тест только если он фиксирует от возможной новой readiness-блокировки.
5. **Fact presentation:** accepted+needs_operator history, configured+failed optional profile, generic/filter empty, brief остается escaped text, критерии открыты, canonical enum доступен в technical details.

Нужен браузерный приёмочный прогон построенной exact revision, потому что static markup не подтверждает фокус, viewBox, масштаб и scroll. Основная матрица: 1434×642 и 1434×900, 1280×800, граница 1100/1101, 800×600; 390×675 — secondary smoke. RU/EN, dark/light, browser zoom 100%/125%; 7/20/50 агентов, 14/40/128 задач. Нагрузочная характеристика в отчёте только после измерения, не по DOM-count.

В отдельном локальном test-проекте проверить реальные записи найма, методы/config save, supervisor/link после перечитывания, message+attachment и conflict/error. Не использовать реальный Blizhe для доказательства новой записи. Если запуск провайдера недоступен, builder честно сообщает это и подтверждает подготовку/mock states; успешный реальный run не выдумывается. Population Gallery, доставка и ответ требуют собственных фактов.

Для приемки навигации фиксировать не только screenshots, но также before/during/after map rect **и** точный viewport; activeElement и его rectangle; library scroll/filter/opener; API request log. Для UX-01 сохранить effective screen text/button measurements и демонстрацию перехода обзор→рабочий масштаб. Итог handoff должен указать exact source revision/dirty-diff digest и asset digests.

## Разрешение спорных предложений

- Постоянная боковая деталь отвергнута: противоречит пользовательскому контракту. Средний composer и большая task detail совместимы.
- «Send запрещён до active» отвергнуто: первый Grok вывод основан на пустом поле и неверно выводит причинность UNKNOWN. UNKNOWN help принят, новая блокировка — нет.
- Безусловный auto-fit при resize отвергнут: стирает ручную рабочую точку. Приняты сохранение центра/zoom и явное восстановление обзора.
- Перестройка 1100 breakpoint откладывается до измерения панелей на типовом рабочем цикле. В этой волне он остается явным проверяемым компромиссом, не вымышленным P1.
- Скрытие исторического needs_operator после accepted отвергнуто; приняты разграничение секций/подписей и сохранение точных данных.
- Преобразование skill slug в выдуманное «человеческое имя» отвергнуто. Использовать каталог и его exact исторические refs; плохие имена данных отдельно фиксировать.
- Полная tab-scoped config запись не обязательна здесь. Самый безопасный scope — честно назвать существующие две области и обозначить config dirty по вкладкам. Если Sonnet предлагает tab-scoped save, прежде решения нужен контракт budget/tool/grants validation для частичной записи; молча менять его нельзя.
- Кластеры, новый layout engine, переработка всей Gallery, новый permission model и массовая CSS уборка не требуются для UX-01–19. Их нельзя объявлять реализованными по этой волне.

Я поддерживаю эту волну как ограниченную и реализуемую. До живой проверки записи/запуска/filled Gallery результат называется улучшенным frontend с перечисленной проверкой, а не полностью удостоверенной эксплуатационной готовностью.
