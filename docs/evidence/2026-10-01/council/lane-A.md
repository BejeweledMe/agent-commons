# Независимый аудит A: архитектура, исполнение и завершённый пользовательский путь

1 октября 2026. Граница: `/private/tmp/commons-council-20261001/source`, снимок HEAD `aa9d373` с имевшимися незакоммиченными изменениями; канонические записи и исходный checkout не изменялись. Прочитаны контракты, оба действующих плана, handoff 21 сентября, исходники Work/outputs/runtime, соответствующие тесты, выборка `TASKS.json`, findings и decisions. Это статический аудит: приложение, тесты, benchmark и реальные провайдеры мной не запускались. Запрошенная линия — GPT-6 Astra; отдельного достоверного runtime-аттестата фактически исполняющей модели в доступных данных нет. Ответы других линий не читались.

**Главный вывод:** у проекта сильное ядро учёта и проверки, но обещание «агент создал продукт — я открыл его работу» пока реализовано фрагментами. Нужен один сквозной инкремент, соединяющий исполнение, долговечный результат, карточку агента, граф и review. Переписывание леджера, переход на сторонний tracker или замена брокера агентным фреймворком этого разрыва не устранят.

## 1. Что действительно существует

Это локальное приложение с React/Vite Work и отдельной Gallery, Python service/domain слоями, неизменяемыми событиями и восстанавливаемыми проекциями. Доска агентов и граф задач — разные представления: первая уже использует React Flow, второй написан на SVG. Провайдеры запускаются внешними CLI через фиксированные профили и ограниченный MCP-каталог, а не прямыми вызовами OpenAI API (`runtime/model.py:742–845`, `runtime/adapters.py:163–178`). Есть ограничения попыток, времени, независимое завершение review, типизированные причины остановки и изоляция operational state.

Самая ценная часть — серверный жизненный цикл. `domain/lifecycle.py:310–369` проверяет текущий approved review, независимость, совпадение задачи и ревизии, завершение делегированного review и отделение reviewer от авторов работы. Сохранять это важнее косметического сокращения числа статусов. Completed, succeeded, approved и accepted описывают разные факты.

Исторические P0 нельзя автоматически объявлять текущими: WP-40 и WP-41 числятся accepted в `TASKS.json`; код preflight проверяет snapshot и MCP handshake, DTO содержит `stop_reason`. Но наличие этих исправлений не доказывает нынешний полноценный frontend-run. `docs/BROKER_OPERATIONS.md:152–160` всё ещё требует release evidence для точной версии: macOS/Linux canary, 100 последовательных герметичных контрактных прогонов на провайдера, 20 реальных запусков без process/canonical mismatch. Задачи L1/R2 в снимке остаются ready. Следовательно, «провайдеры квалифицированы когда-то» и «релиз проверен сейчас» нельзя смешивать.

Особенно важно не затереть чужую незавершённую работу: план и задача WP-20 называют bulk receipt load следующим этапом, однако снимок уже содержит `ReceiptRecoveryView`, `load_recovery_view()` и передачу одного view через reconcile/status (`storage/receipt_recovery.py:147–195, 467–503`). Lock-scoped verified ledger view также существует (`services/manager.py:481–493, 822–826`). Нужны review и измерение текущего WIP, а не повторная реализация по старому плану. Цель ≤1 с на 3206 событиях не подтверждена этим аудитом; прежние 33 с тоже нельзя выдавать за актуальное измерение.

## 2. Решающие пробелы и блокеры

**P0 для заявления «рабочий продукт»: нет предъявленного в этой границе доказательства полного текущего пути.** Воспроизвести на отдельном проекте: hire → task → implementation → публикация результата → terminal outcome → независимый review → человеческая приёмка. Включить настоящее изменение файлов и запуск frontend, а не только чтение MCP. Preflight доказывает ограниченные свойства среды; наличие контрольного файла и каталога инструментов не доказывает, что выбранный worker действительно умеет собрать приложение, держать сервер и передать результат. Отказ должен происходить до оплачиваемого запуска там, где его можно определить заранее; фактический отказ во время работы должен оставлять понятную причину и восстановление.

**P1, основной пользовательский запрос: карточка агента не ведёт в его галерею.** В `ProjectBoard.tsx:31–48` имя — обычный `span`, у карточки нет маршрута открытия. Есть отдельная `OutputsButton`, но `OutputsPanel.tsx:54–56` возвращает null при отсутствии результата и при неизвестном количестве. Ошибка чтения и реальное «ничего не создано» делают точку входа одинаково невидимой. Это противоречит требованию пользователя и нуждается в явном уточнении существующего frontend-контракта, который пока требует count для Results-кнопок. Постоянный переход через имя/аватар должен работать независимо от count; count остаётся факультативным бейджем.

**P1, происхождение теряется по дороге к человеку.** Backend несёт task revision, artifact/content revision, producer session/agent/delegation (`services/outputs.py:82–110`), доказательство автора выводится из канонической цепочки, не из назначения задачи (`216–250`). Клиент проверяет эти поля, затем выбрасывает их из модели (`outputsTypes.ts:78–97, 114–129`). Поэтому панель не может дать переход в исходную задачу, прогон и точную версию. Это преимущественно разрыв DTO→view-model→UI, а не основание выдумывать новый источник истины.

**P1, история — пока не обещание сохранённых версий.** Публикация generated image регистрирует путь и хеш, возвращает `content_copied: false`; документация инструмента прямо предупреждает, что перезапись source делает старое изображение stale (`mcp/design_output_tools.py:49–56, 149–172`). Для formal design package старые версии также остаются stale, без загрузки исторических байтов (`outputs.py:153–164, 377–382`). Просмотр generated history после завершения задачи уже поддержан, но только пока исходные байты совпадают. Следовательно, UI «История» нельзя продавать как сохранённые изображения. Нужен bounded immutable blob store либо обязательные неперезаписываемые versioned файлы с проверенной доступностью. Старые потерянные байты нельзя восстановить миграцией метаданных.

**P1, frontend preview — объявление адреса, а не обслуживаемый frontend.** `live_previews.py:1–7, 55–73` намеренно не управляет процессом и не проверяет reachability; TTL 60–3600 с, записи после срока плюс 24 часа перестают возвращаться (`473–475`). Прямая успешная terminal-последовательность сохраняет ссылку до исходного TTL, но не продлевает жизнь сервера (`126–171`). Такой механизм полезен и честен, однако frontend-портфолио требует устойчивого build artifact и явно управляемого «открыть/запустить/остановить preview». Сборка и сервер должны принадлежать операторскому механизму с lifecycle, а не случайному дочернему shell-процессу агента. Первый инкремент можно ограничить статическим frontend build; динамические приложения обозначить отдельным поддерживаемым типом, а не обещать любой full-stack preview.

**P1, review исторического результата неоднозначен.** `outputs.py:264–270, 437–469` присоединяет последний текущий review по task ID ко всем результатам этой задачи, не по `item.task_revision`. По существующему контракту это review производящей задачи, не самого изображения; это не доказанный обход acceptance. Но возле старого изображения слово «одобрено» легко считывается как одобрение именно этой версии. Разделить «проверка версии результата» и «сейчас у задачи»; показывать reviewed revision и привязки evidence. Для live preview review вообще отсутствует в типе. Нужны тесты: R1 output → правка задачи R2 → approved R2, без автоматического одобрения R1.

**P1, карта непригодна как общий обзор крупного проекта.** Лимит 128 задан в `taskGraph.ts:8`; `TaskViews.tsx:42, 98–105` подменяет карту списком ещё до вычисления связанного подграфа. Даже маленькая выбранная компонента не спасёт большую общую выборку. Раскладка делает до четырёх узлов на строку, сортирует по ID и не учитывает пересечения (`taskGraph.ts:51, 81–97`). Есть keyboard navigation, выявление цикла и отсутствующей зависимости, честный fallback. Но это dependency DAG, не декомпозиция продукта: `tracker_dtos.py:18–45` содержит objective/application/dependencies, без parent-task или component relation. Эти понятия нельзя получать из похожих названий или department frames.

**P1, масштаб чтений и доверие к latency.** Каждая видимая Results-кнопка перечитывает summary раз в 15 секунд (`OutputsPanel.tsx:40–49`), а каждый summary строит snapshot, индексы producer и перебирает результаты (`outputs.py:179–251`). После добавления постоянных точек входа не запускать отдельный полный проход на каждую карточку: запросить batch counts либо snapshot-scoped проекцию с проверенной инвалидизацией. Предел 64 outputs сейчас даёт отказ всей выборки (`147–152`), поэтому нужны пагинация или фильтры с честным total, не увеличение лимита вслепую.

## 3. UX для сильного разработчика

Агент открывается через имя/аватар и клавиатуру в отдельный workspace результатов с устойчивым URL и возвратом к прежнему положению доски. Drag и кнопки карточки не вызывают переход. Внутри: краткое имя/специализация, фильтры «Все / Приложения / Макеты», задача, дата, версия, статус доступности, review. Главная область показывает thumbnails или preview; боковая — связанный task/run и причины ограничений. Технические идентификаторы, хеши, provider/profile и точные ревизии доступны в компактном раскрытии с копированием. Не скрывать значимые технические детали от целевой аудитории; убрать лишь бесконечное дублирование и шум.

Не нужен жёсткий фильтр «дизайнер = только PNG, frontend = только URL»: специализация задаёт начальный акцент, а принадлежность определяется доказанным producer. Для пустого агента — «Результатов пока нет» и переход к его задачам; для сбоя — отдельная ошибка/повтор; для stale — предыдущая версия с причиной; для expired preview — сохранить build и предложить новый запуск. Просмотр сам по себе ничего не запускает. Не передавать Commons-cookie, capability или рабочую директорию недоверенному preview; отдельный origin остаётся обязательным.

В трекере нужны два масштаба: обзор целей/компонентов и DAG выбранной группы. Для первой версии группировать по существующим objective/application; сущность компонента и parent/child вводить только после явного контракта, отдельно от dependency. Рёбра подписывать по смыслу; у каждого узла — имя, исполнитель, состояние, блокирующая причина и наличие результата. Click открывает инспектор, инспектор — результат. Collapse групп, upstream/downstream focus, поиск, fit/zoom, keyboard/list equivalent важнее красивой анимации. Прогресс — «5 принято из 8; 2 на проверке; 1 заблокирована», не выдуманный процент исполнения. Critical path уже обозначен как `dependency_depth_only`, `predictive: false` (`tracker_dtos.py:111–114`); не превращать его в прогноз срока.

## 4. Порядок работ и проверяемые пакеты

1. **Сверка baseline и текущего WIP.** Зафиксировать source manifest, рабочие изменения и canonical task IDs; обновить статус WP-20 по факту, не принимать автоматически. Координатор: targeted tests, полный `make check`, измерение write/read latency на синтетическом размере 3206 и текущем порядке 4212 событий. Приёмка: воспроизводимый отчёт, неизменный golden replay, crash/retry/concurrent-writer проверки. Реестр предупреждений doctor разделить на исторические и действующие; массовое invalidation ради нуля предупреждений запрещено смыслом модели.

2. **Исполнение и перенос моделей.** Зависит от baseline. Подтвердить точный CLI, MCP build, модель и инструменты; выполнить новый canary builder/reviewer и короткий реальный frontend output run. Приёмка: файл создан, публикация привязана, terminal outcome один, дочерняя сессия закрыта, ошибка/отмена не превращаются в success. Это P0 gate для следующих сквозных доказательств.

3. **Контракт результата.** Зависит от 1; frontend-разработка может начаться на fixtures. Добавить сохранение producer/task/run/revision в клиентской модели, version identity и bounded retention, разделить review semantics, согласовать статический preview lifecycle. Миграция аддитивная: старые записи остаются читаемыми с unknown/unavailable; никакого приписывания автора или старых bytes. Приёмка: смена producer, повтор публикации, потеря файла, restricted reclassification, stale review, истечение TTL и перезапуск сервиса не дают ложного current/approved.

4. **Агент → галерея.** Зависит от 3. Постоянный доступ через карточку; маршрут/назад; thumbnails, версии, task/run links; loading/empty/error/expired; batching counts. Приёмка: EN/RU, 360px и desktop, keyboard/focus, переключение проекта при незавершённом запросе, 0/1/65 результатов, отсутствие межпроектного смешивания. Оба модульных frontend и строгие парсеры проверяются вместе с backend DTO.

5. **Граф продукта и задач.** Зависит от 1, использует переходы 4. Сначала существующие objective/application + dependency DAG; затем узкий ADR для истинной декомпозиции, если она нужна. Сравнить улучшение текущего layout с React Flow на реальных fixtures; последний уже установлен, но CSP и доступность подтвердить в браузере. Приёмка: 1/20/128/304 задач, diamond dependencies, длинная цепочка, несколько компонент, скрытые prerequisites, cycle/missing references; выбор небольшого подграфа работает независимо от общего размера.

6. **Интеграция и выпуск.** Один asset-интегратор пересобирает Work/Gallery; source/bundle parity, TypeScript, Node suites, полный `make check`, wheel smoke, live evidence точной версии. Пока независимое review работает, checkout и ledger неподвижны. После approved — человеческая acceptance. Обновить единственных владельцев документации и активный план; не превращать архивы и все ready-задачи в новый бесконечный backlog.

Минимальный первый законченный инкремент: один дизайнер публикует две сохранённые версии макета, frontend-агент создаёт один статический build, пользователь с карточек открывает именно их результаты, видит происхождение и состояние review, из небольшого DAG переходит в задачу и результат. Затем изменяется задача: прежний результат остаётся доступен как исторический, прежнее одобрение не переносится. После перезапуска приложения build/изображения сохраняются; expired сервер не выдаётся за работающий. Это проверяемая демонстрация основного обещания, а не серия отдельных зелёных пакетов.

## 5. GPT-6 и распределение ответственности

Для начала pin `model` в операторском Codex profile: код уже передаёт `--model`, а `--ignore-user-config --strict-config` исключает надежду на домашний конфиг (`model.py:826–845`). У профиля нет поля reasoning effort (`742–750`); если оно нужно, вводить типизированный allowlist, фиксированный CLI mapping и включать в qualification fingerprint. Не добавлять произвольные argv. Существующий fingerprint уже включает model, launch policy, исходники и executable bytes (`provider_qualification.py:152–193`). Каждый изменённый профиль требует собственной квалификации; receipt одного profile ID нельзя считать одновременно доказательством нескольких моделей.

Предлагаемые роли — гипотеза до project eval: GPT-6.1 Sol для основной реализации; Astra для архитектуры, lifecycle/storage и независимой проверки сложных изменений; Luna для ограниченной механики/локализации после теста на соблюдение контрактов. Claude оставить вторым независимым reviewer и кандидатом на UX/front-end реализацию. Grok не делать обязательным звеном critical path, пока точная версия не проходит terminal-tool eval: findings фиксируют повторяющийся exit 0 без terminal tool, а отдельный Linux-инцидент — обход через CLI. Новый красивый prompt не заменяет проверку результата.

Официальные OpenAI-сведения о позиционировании моделей предоставлены координатором со ссылками на latest-model и gpt-6.1-sol; я их независимо не перепроверял. Здесь не нужен API migration. Если позже появится прямой OpenAI adapter, тогда отдельно применимы Responses/tool-calling и ограничения reasoning/sampling, без переноса API-параметров в несуществующие CLI-поля.

Project eval: одинаковые небольшие пакеты (DTO+parser, revision/retry, layout+a11y, файл→publish→terminal, независимое обнаружение посеянного дефекта), одинаковые права и бюджет; измерять first-pass acceptance, пропущенные дефекты, корректные terminal calls, вмешательства координатора и wall time. Денежный расход показывать только если он измерен: текущие adapters объявляют `UsageReporting.NONE` (`adapters.py:172–178`). Согласие моделей — источник вопросов, не доказательство.

## 6. Риски и несогласие

Не согласен с безусловным «сначала закрыть все старые runtime-задачи, потом UX»: завершить один реальный gate необходимо, но его scope должен быть ограничен пользовательским инкрементом. Макеты и контракт результатов можно готовить одновременно в отдельных checkout. Не согласен и с автоматической заменой SVG на React Flow: библиотека не создаёт модель компонентов и не исправляет скрытые зависимости сама.

Самые дорогие повторы прошлых ошибок: старый installed uv tool после изменений `src/**`; canary не той модели/ревизии; изменение checkout во время review; строгий клиент отвергает аддитивное поле; owner принимает prose/exit 0 за terminal completion; новый run теряет рабочий checkpoint; перегруженный план маскирует отсутствие браузерной демонстрации. Перед следующим backend-run удалять stale build, переустанавливать worker MCP из точного checkout и квалифицировать профиль, который действительно будет запущен. Один writable worker на checkout, один сборщик ассетов, фактические сценарии поверх tests — это эксплуатационные условия результата, а не бюрократическое приложение к нему.
