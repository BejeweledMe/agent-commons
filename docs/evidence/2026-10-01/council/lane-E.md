## 1. Что действительно есть

Work — React/Vite/TypeScript, Gallery — отдельное приложение; оба собираются в поставляемые wheel-assets. Это не прототип, требующий npm у конечного пользователя (`docs/FRONTEND_CONTRACT.md:3–9`). Каноническая цепь «агент → задача → прогон → review → человеческая приёмка» записана в продукте (`docs/PRODUCT.md:73–92`); клиент не должен подменять её собственными состояниями.

Доска уже использует React Flow: стоящие агенты, связи из graph DTO, отделы как пользовательская раскладка, fit/zoom/minimap и CAS-сохранение. Кнопки Conversation, Results, Tasks и Give a task существуют (`frontend/work/src/components/ProjectBoard.tsx:31–48, 95–138, 168–195, 211–217`). Это граф агентов; требуемый граф задач — другая поверхность, её нельзя выдавать за ту же структуру.

Граф задач тоже существует: детерминированный DAG сверху вниз, статус, исполнитель, текущая фаза, выбор задачи, клавиатурная навигация, фокус связанного подграфа. Для циклов/отсутствующих prerequisites предусмотрен отказ от выдуманного DAG (`frontend/work/src/taskGraph.ts:49–99`; `components/TaskGraph.tsx:20–53`). Тесты действительно проверяют направление, устойчивость порядка, цикл, отсутствующую зависимость и большой граф (`frontend/work/tests/task-graph.test.mjs:61–83`). Следовательно, пакет следует назвать улучшением карты задач, а не реализацией графа с нуля.

Outputs сервис уже строже простого портфолио: scope применяется до проверки байтов и выбора версии; владелец выводится из уникальной связи artifact actor → child session → delegation → task → agent, а не из текущего assignee (`src/agent_commons/services/outputs.py:216–249`; `generated_outputs.py:21–39`). Изображения имеют точные task/artifact/content bindings, историю, актуальность и nullable review_state (`outputs.py:82–110, 251–275`). Это полезная защита от присвоения чужой работы и выдачи старых байтов за текущие.

Live preview уже можно публиковать через MCP, но registry — объявления адресов, а не управление процессом (`src/agent_commons/mcp/live_preview_tools.py:21–45`; `runtime/live_previews.py:1–3, 454–519`). UI открывает отдельную вкладку, повторно проверяет срок и origin, не внедряет приложение в доверенный iframe (`frontend/work/src/outputsTypes.ts:131–143`; `components/OutputsPanel.tsx:117–126`). Нельзя называть reported_ready доказанной доступностью frontend.

## 2. Приоритетный реестр разрывов

**P0 — закрыть проверяемость основного цикла.** Исторический dogfooding описывает реальные остановки, ручную регистрацию и неполученную приёмку (`docs/handoffs/2026-09-21-blizhe-dogfooding-feedback.md:413–431, 462–488`). Но считать старые UX-19/21/10 неизменными открытыми дефектами нельзя: TASKS.json содержит accepted WP-40 и WP-41; текущее `tests/runtime/test_preflight.py:232–297` проверяет MCP handshake, отсутствие executor control и нечитаемый snapshot, а `tests/ui/test_tracker_reads.py:350–398` — server-derived stop_reason. Нужен новый bounded smoke на стабильной установке: создание задачи → реальная правка → зарегистрированный результат → независимый review точной ревизии → человеческая приёмка. До него честный статус — «исправления представлены кодом и тестами; живой результат не подтверждён», а не «всё сломано» или «готово».

**P0 — ложный зелёный статус карты.** `frontend/work/src/taskGraph.css:20` использует accepted-зелёный одновременно для `completed` и `accepted`. Только двойная рамка различает состояния. Это прямо против `docs/PRODUCT.md:44–46` и `docs/FRONTEND_CONTRACT.md:211–212`. Более того, `frontend/work/tests/task-graph.test.mjs:85–99, 132–140` закрепляет общие accepted-токены. Исправлять нужно CSS и тест: completed нейтрален, green зарезервирован для acceptance. Баг небольшой по объёму, существенный по доверию.

**P1 — точный запрос «клик на агента открывает его галерею» не выполнен.** У card/name/icon отсутствует navigation handler: только отдельная Results-кнопка (`ProjectBoard.tsx:31–48`). `OutputsAction` возвращает null при count=null и count≤0 (`OutputsPanel.tsx:54–56`), поэтому новый агент и сбой summary выглядят как отсутствие функции. Empty/error внутри диалога есть (`:100`), но обычный вход к ним скрыт. Это сознательный существующий контракт: `frontend/work/tests/outputs.test.mjs:52–57` требует кнопку только для положительного количества. Изменение требует пересмотра именно этого поведения, а не объявления тестового провала случайностью.

**P1 — происхождение теряется на клиенте.** Wire сохраняет task_id/task_revision, producer и recorded_at (`src/agent_commons/ui/output_routes.py:79–105`), однако parser возвращает ImageOutput без этих полей (`frontend/work/src/outputsTypes.ts:6–12, 94–97`); карточка показывает title/status/count, без перехода к задаче (`OutputsPanel.tsx:100–105`). Gallery показывает техническую provenance, но на уровне текущих Design Packages, не agent scope (`services/design_gallery.py:138–169`; `frontend/gallery/src/main.tsx:86–92, 419–454`). Для требуемой персональной галереи лучше расширить Work outputs, сохранив Gallery как авторскую поверхность пакетов.

**P1 — проверка версии результата двусмысленна.** review_state присоединяется по task_id ко всем версиям (`outputs.py:264–271, 445–469`), в том числе historical. Это состояние текущей проверки задачи, а не доказательство проверки конкретного изображения. Live DTO вообще не несёт review (`ui/output_routes.py:115–135`). Нужно явно писать «проверка задачи» и давать target revision, либо добавить проверку совпадения с точной binding результата. Принятая новая задача не делает старый макет одобренным.

**P1 — история ограничена и неоднородна.** Outputs list отказывает при >64 элементах, без пагинации (`outputs.py:147–152`); Gallery ограничивает всю коллекцию 64 screens (`design_gallery.py:26–27, 151–162`). Generated series зависит от delegation_id и path (`generated_outputs.py:17–18`), поэтому новый прогон может образовать новую серию, а не следующую версию логического результата. Live history — временное operational state с expiry/retention (`live_previews.py:473–475`). Нужны явные границы истории, безопасная пагинация и согласованный логический result slot; нельзя обещать вечную историю живых процессов.

**P1 — карта перестаёт быть картой на реальном масштабе.** MAX_GRAPH_TASKS=128, а TaskViews проверяет весь visibleTasks до mounted focused graph (`taskGraph.ts:8`; `components/TaskViews.tsx:42, 98–105`). Даже маленькая связанная компонента выбранной задачи не помогает, если фильтр оставил 129 задач. При 304 задачах снимка это существенный сценарий, хотя не все 304 обязательно одновременно видны. Раскладка по четыре узла в строке, сортировка по ULID, кривые напрямую между центрами не уменьшают пересечения (`taskGraph.ts:51, 81–97`). Нет группирования по цели/application, collapse, поиска по узлам, fit/zoom карты и выделения prerequisites/dependents.

**P1 — профиль изменился, но UI говорит «проверка провалилась».** Несовпадение fingerprint и qualified=false всё ещё сведены в PROVIDER_QUALIFICATION_FAILED (`runtime/provider_qualification.py:364–390`). Изменение модели, исходников или бинарника требует переквалификации; fingerprint это правильно учитывает (`:167–190`). Различать missing/failed/runtime_changed/invalid_receipt нужно до миграции моделей, чтобы повторные canary были понятны.

**P1 — latency и release evidence остаются отдельными обязательствами.** WP-20 в TASKS.json ready: принято только option A; summary сообщает small benchmark 3.28→2.26 с, а не достижение ≤1 с на 3206 событиях. ADR 0023 одновременно draft/not authorized (`docs/adr/0023-incremental-ledger-validation.md:3–9`). Нужно согласовать документационную границу принятого варианта и измерить B, сохранив corruption/concurrency/retry guarantees. Не превращать draft в разрешение на durable poisoned cache. L1 authenticated Linux и R2 exact release evidence в TASKS.json ready; отсутствие результата не равно доказанной неисправности Linux.

## 3. Целевой UX для технического разработчика

Клик по имени/аватару агента и Enter открывает стабильную agent-scoped галерею; drag двигает карту; порты и action-кнопки не открывают галерею. Вход есть всегда, count — дополнительная информация. Scope виден в заголовке: проект, агент, специализация. Сохраняются выбор задачи/вид/фильтр; возврат восстанавливает фокус. Пусто означает «результатов ещё нет» с задачами агента и действием создания/выбора задачи. Failed summary не должен выглядеть как пустая коллекция; ошибки scoped list показывают bounded причину и Retry.

Основной вид — последние результаты по логическим сериям с thumbnail, задачей, временем, типом и версией. Переключатели «Последние / Все версии», фильтр задачи и типа. Inspector результата показывает изображение или live-ссылку, provenance и exact bindings в раскрытии; рядом доступны «Открыть задачу», «Разговор», «Проверка». Для frontend-агента основной результат — отдельно открываемый frontend и screenshot; для дизайнера — экраны/варианты и сравнение двух проверенных версий. Тип определяется опубликованным результатом, не названием роли: инженер может создать макет, дизайнер — работающий prototype. Исторические verified pixels доступны как история, never-current. Preview expired, process absent, origin reported unavailable и review returned — разные причины с разными действиями.

Карта задач начинается с текущей цели или blueprint application. Это имеющаяся provenance (`ui/tracker_reads.py:201–202, 431–449`), а не выдуманное parent-child отношение. Структура проекта/компоненты появляется только при отдельном подтверждённом поле или сохранённой пользовательской группировке; зависимости не объявляются декомпозицией. Нельзя автоматически считать папку, department frame или agent роль компонентом продукта.

Узел содержит результат задачи, реального/предложенного исполнителя с явным различием, task state, observed run phase и причину блокировки. Двойной клик/Enter открывает inspector; одиночный клик выделяет связи и ближайшие prerequisites/dependents. Нужны fit, zoom, поиск, показ скрытых границ фильтра, collapse settled tasks и обзор групп с точными счётчиками accepted/completed/review/blocked. «Прогресс 3/8 принято» допустим; прогноз даты и critical path как времени недопустимы без duration data. Large mode рисует ограниченную компоненту/группу плюс обзор, а не молча заменяет продуктовую карту списком. Mermaid/SVG export полезен локально, интеграции Linear/Jira не входят в первый increment: решение владельца сохраняет local-first (`docs/handoffs/2026-09-21-council-product-direction.md:177–179`).

Для опытной аудитории приоритетны быстрый переход task↔agent↔result, command palette, keyboard navigation, copy IDs/revisions, видимые причины остановки, retained drafts и проверяемое соответствие installed runtime исходникам. Технические детали доступны по запросу; прятать их полностью или заставлять читать одинаковые onboarding-абзацы на каждом экране не следует. Продуктовый glossary можно уточнить под теперь явно заданную аудиторию, сохранив одну owning page.

## 5. GPT-6 и распределение моделей

Текущий runtime запускает CLI: Codex profile.model передаётся в `--model`, с strict config и контролируемым MCP (`runtime/model.py:743–750, 814–841`); Claude и Grok имеют аналогичные profile.model. Нет оснований требовать миграции на Responses API как части данного запроса. Нормализованные кандидаты: `gpt-6.1-sol` для большинства coding/DTO/tests, `gpt-6-astra` для lifecycle/security/storage design и независимых проверок, `gpt-6-luna` для bounded механических изменений. Это стартовые роли, не измеренный рейтинг качества.

Конкретные pins должны быть проверены installed CLI и отдельным canary builder/reviewer. Не оставлять model=null, если требуется воспроизводимая модель. Новую настройку reasoning нельзя считать уже поддержанной полем profile: в прочитанном Codex dataclass её нет. Если она нужна, добавить разрешённую конфигурацию, argv tests и fingerprint binding. Официальные OpenAI сведения предоставлены координатором в brief и мной независимо не перепроверялись; ограничения API temperature/Responses не нужно переносить на CLI без проверки его контракта.

Claude полезен как независимый frontend/UX reviewer и второй implementation вариант; Grok — ограниченная механика после успешной квалификации, а не критический lifecycle owner по привычке. Исторический план отмечает повторные выходы Grok без terminal tool (`docs/plans/2026-09-09-ux-closure-tech-plan.md:741`); это прошлое наблюдение, не вывод о современной модели. Смена семейства усиливает разнообразие проверки, но независимость определяется отсутствием авторства exact revision.

Representative eval: один и тот же immutable starting snapshot, 6–8 bounded задач (gallery zero/error entry, provenance parser, 130-task focused graph, green invariant, preview lifetime, terminal MCP outcome, concurrency/corruption patch). Оценивать hidden behavior checks, корректный terminal outcome, сохранность границ, человеческие правки и длительность; считать provider attempts и лимиты, не выдумывать денежный spend. Builder canary проверяет механизм, project eval — качество продукта. Результат назначает модель пакету; fallback не меняет проверяемый контракт.

## 6. Опыт, который нельзя потерять

`make check` — единственный green contract (`CONTRIBUTING.md:23–29`; `Makefile:18–53`); tsc и browser scenario нужны дополнительно по типу изменения, а passing source regex не доказывает взаимодействие. Один writable worker на checkout, review на неподвижном exact revision, один asset integrator на волну, rebuild tracked bundles и wheel smoke обязательны. После source изменений переустановка MCP и canary следующего профиля защищают от реально пережитого installed-source drift. Журнал не лечится массовым удалением предупреждений: stale review — факт прежней ревизии, а не автоматически ошибка; правило адресного repair уже записано (`docs/plans/2026-09-18-consolidation-and-wave-4-plan.md:130–153`).

Я не согласен с автоматическим повторным открытием всего архивного backlog или с утверждением, что UI-only редизайн доведёт продукт до рабочего состояния. Согласен с быстрым визуальным исправлением галереи/карты параллельно подготовке стабильного runtime, при раздельных checkout; проверять итог надо на настоящих результатах. Ещё один консилиум не заменит этот вертикальный пользовательский проход. Нужен один зафиксированный результат с проверкой, наблюдаемыми отказами и работающими переходами — затем расширение масштаба.
