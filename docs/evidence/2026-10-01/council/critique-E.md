## Проверенные различия и поправки

**1. Response A точнее учитывает незакоммиченный WP-20.** Я в E сослался на ready task и summary о следующем option B, но недостаточно проверил фактический WIP. В коде действительно уже есть передача `receipt_view` в `status`, чтение reservations/abandonments/reconciliations из него (`src/agent_commons/storage/receipt_recovery.py:147–195`), а `assert_write_allowed` загружает один view и передаёт его через reconcile/status (`:467–503`). Следовательно, «реализовать B» заменить на «проверить текущую реализацию B, исправить обнаруженное, измерить и пройти review». Документы/задачи здесь отстают от кода. Ни A, ни E не предъявляют нового замера ≤1 с на 3206 событиях; нельзя объявлять цель достигнутой или воспроизводить исторические 33 с как сегодняшнее значение.

**2. Response A добавляет существенную проблему долговечности изображений.** Она подтверждается: MCP-инструмент обещает запись metadata, предупреждает о stale после смены source (`src/agent_commons/mcp/design_output_tools.py:49–56`) и возвращает `content_copied: False` (`:149–172`). E заметил неоднородность истории и delegation-based series, но недооценил отсутствие сохранённых старых байтов. Для минимального increment достаточно versioned неперезаписываемых путей и их проверенной доступности; новый blob store не должен стать обязательной предварительной миграцией всей архитектуры. Однако продукт обязан явно отличать сохранённый результат от ссылки на изменяемый файл. Нужен сценарий «опубликовать R1, создать R2, перезапустить сервис, открыть R1».

**3. Response E добавляет конкретный баг доверия карты, пропущенный A.** `frontend/work/src/taskGraph.css:20` красит completed и accepted одинаковыми accepted-токенами; `frontend/work/tests/task-graph.test.mjs:85–99` закрепляет это поведение. Это противоречит `docs/PRODUCT.md:44–46`. Исправление нейтрального completed и регрессия «зелёный только accepted» входят в самый первый frontend-пакет. Это семантический дефект, но приоритет P0 следует понимать как stop-the-line для честного UI, а не доказательство повреждённого ledger.

**4. Оба ответа верно находят ограничение >128, но план приёмки нужно уточнить.** `TaskViews.tsx:42, 98–105` решает fallback раньше focused component. Просто убрать эту проверку недостаточно: `taskGraph.ts:49–53` снова ограничит компоненту >128. Нужны отдельно «304 всего, компонент 5» и «компонента сама >128». Первый сценарий должен давать граф; второй — честную навигацию к ограниченному neighbourhood/группе и доступный список. По существующим objective/application допустимо группирование, но не утверждение о канонических parent/component отношениях: `src/agent_commons/ui/tracker_dtos.py:18–45` их не содержит. Фильтр обязан показывать число скрытых prerequisites, иначе dependency graph выглядит полным при утраченных границах.

**5. Review-state проблема — UX двусмысленность, не доказанный bypass.** A правильно оговаривает это; формулировку E сохранить с таким уточнением. Сервис присоединяет review по task ID (`services/outputs.py:264–271, 445–469`), а acceptance остаётся другим lifecycle. Для старого output не выводить «эта версия одобрена» из нового task review. Проверить R1 output→R2 task→approved R2, включая nullable/unknown поля.

**6. Polling — риск масштаба, не ещё измеренный тормоз.** A указывает на повторные summary, но `frontend/work/src/outputsApi.ts:33–42` уже deduplicates один scope и кеширует его на 14 секунд. Между разными агентами это не устраняет полный backend проход; при 100 карточках batch counts полезны. В первом постоянном входе допустимо вовсе не ждать count для навигации. Не утверждать линейный сетевой шторм без измерения cache/projection/runtime поведения.

## Сводный путь реализации

Первыми зафиксировать baseline/WIP и точные runtime identities. Фронтенд выполнять на fixtures в изолированной копии, пока квалификация провайдеров блокирована: E0 не должен запрещать всю обратимую разработку до успешной внешней авторизации. Сам консилиум не даёт права обходить auth или подменять требуемую модель.

Первый пакет: постоянный card/name entry в scoped outputs при 0/loading/error; сохранить task/producer/revision в parser; переход gallery↔task; neutral completed; focused graph при большой общей выборке; count скрытых зависимостей, fit и понятная навигация. Приёмка — EN/RU, keyboard/focus, переключение проекта при pending request, fork/join и большой synthetic project. Graph search/группы и durable version storage расширяют этот increment после основных переходов. Drag/ports/button clicks не должны непреднамеренно открывать gallery. React Flow не является обязательным решением: улучшение текущего SVG проще, если удовлетворяет CSP и навигации.

Следующий пакет: дизайнер с двумя сохранёнными версиями и frontend-агент со статическим build на отдельном origin. Открытие результата не запускает процесс автоматически. Включить expired preview, overwritten image, reclassification, review R2 при historical R1 и перезапуск приложения. Только затем настоящий provider implementation→terminal→independent exact review→human acceptance.

GPT-6 migration начинается с явного profile.model и квалификации installed CLI; Sol/Astra/Luna распределение остаётся гипотезой до одинаковых project eval. Reasoning field сейчас не реализован: новую typed configuration добавлять только при необходимости. Provider diversity полезно, но не заменяет author-independent review. Claude/Grok оставлять вне обязательного пути до восстановления аутентификации; их отсутствие не доказывает непригодность моделей.

Наконец, различать три gates: focused tests/tsc/browser interaction; полный `make check` и wheel assets; экспериментальный broker release gate. Последний явно требует macOS/Linux canary, 100 hermetic runs на провайдера, 20 real launches и нулевой mismatch (`docs/BROKER_OPERATIONS.md:152–160`). Один удачный demo подтверждает вертикальный маршрут, но не весь release gate. До выполнения внешних условий сохраняется честная граница готовности, с точным перечнем оставшихся проверок.
