# Рецензия второго этапа

Прочитаны два успешных ответа, Response A и Response E, и повторно проверены решающие участки immutable source. Response A узнаю как свой первый ответ; совпадение с ним не является независимым подтверждением. Идентичности других авторов не вывожу, модели не ранжирую. Три линии не ответили из-за аутентификации: консенсуса пяти нет. Ни исходники, ни леджер основного проекта не менялись.

## Что подтверждено и что кандидаты дополняют

Оба ответа правильно определили архитектуру и главные разрывы: отдельные Work и Gallery, CLI-профили вместо прямого API, отсутствующий переход с карточки агента, скрытый вход при нуле/ошибке count, отбрасывание provenance клиентским parser, ранний лимит карты 128, неоднозначное присоединение review по task ID. Проверены `ProjectBoard.tsx:31–48`, `OutputsPanel.tsx:54–56`, `outputsTypes.ts:78–97`, `TaskViews.tsx:42,98–105`, `outputs.py:264–270`. Удачно, что ни один кандидат не предлагает заново строить леджер или считать старые UX-19/21 неизменными текущими дефектами.

Response A сильнее раскрывает физическое сохранение результатов: `content_copied:false` действительно означает, что история регистрации не гарантирует доступность прежних изображений после перезаписи файла. A также отмечает стоимость N отдельных summary-запросов и наличие уже написанного bulk-receipt WIP. Эти детали нужны для полноценной галереи, а не только нового маршрута.

Response E добавляет два точных факта, пропущенных A. Первый: `taskGraph.css:20` использует одинаковые accepted-токены для completed и accepted; различие двойной рамкой не выполняет правило «зелёный только после приёмки». Исправить CSS и закрепляющий это тест нужно в первом инкременте. Классификация P0 чрезмерна без принятой общей шкалы: это подтверждённый P1 дефект представления доверия, но серверную приёмку он не обходит. Второй: `provider_qualification.py:385–390` смешивает fingerprint drift и провал квалификации в одном коде. Различение причин особенно полезно при смене моделей. Missing уже имеет отдельный REQUIRED-код (`379–384`), поэтому не следует описывать всё пространство причин как полностью неразличимое.

E также справедливо замечает, что generated series включает delegation ID и path (`generated_outputs.py:17–18`). Значит, «версии» между двумя прогонами не обязательно одна логическая серия. Это отдельный разрыв от сохранности байтов; нужны одновременно устойчивый result slot и exact content identity.

## Поправки и несогласия

Слово P0 у обоих ответов относится преимущественно к отсутствию свежего доказательства end-to-end. Лучше назвать это блокером заявления о готовности, не доказанным падением продукта. L1/R2 ready и исторический неудачный dogfooding определяют незакрытые проверки; не позволяют утверждать, что нынешний Linux или frontend execution сломан.

A предлагает полноценное управление preview-процессом, что архитектурно обосновано, но расширяет минимальный объём. Для первого результата достаточно долговечного статического build и ограниченного сервера отдельного origin с явным запуском; универсальный менеджер dev-серверов/full-stack не нужен. Нельзя одновременно обещать обязательное переживание restart и отложить хранение artifacts: этот dependency нужно сделать явным.

В E первый инкремент E0+E1/E2 обещает исторические изображения и frontend, тогда как полноценные версии и preview вынесены в E3. Если демонстрация использует только существующую регистрацию URL/пути, она покажет переходы, но не надёжное портфолио. Добавить минимальную часть E3 — versioned immutable файлы/build, без общей новой сущности на все типы результатов.

Оба ответа разумно оставляют React Flow решением после сравнения. Замена canvas сама по себе не создаёт компонентную модель. Однозначно разделить objective/application grouping, dependency edges и будущий parent/component relation. В поведении selection есть расхождение: A предполагает click→inspector, E click→selection и double-click→inspector. Выбрать один pattern по текущему `TaskGraph.tsx:31`; для первого инкремента сохранить существующий одиночный переход, без добавления скрытого double-click как необходимого действия.

ADR0023 помечен draft/not authorized (`:4`), хотя A-код и WIP уже существуют. Это документационная рассинхронизация, а не повод уничтожить работу либо обнулить прежнюю авторизацию; проверить точные canonical решения и ревизии. E недостаточно явно говорит, что B уже реализован частично в dirty snapshot. A здесь точнее: сначала аудит готового WIP, затем недостающая работа.

## Новое внешнее доказательство после первых ответов

По отдельному заданию координатора выполнено изолированное воспроизведение WP-20, не являющееся голосом консилиума. Артефакты: `wp20-review/review.md`, `reproduce.py`, `reproduction-result.json` рядом с этим файлом.

Подтверждён P1: `receipt_recovery.py:421–422` импортирует legacy abandonment на диск, не обновляя `receipt_view.abandonments`. При первом v2 reconcile точный tombstone не reconciles, а конфликтующий semantic hash не отклоняется: оба вызова возвращают `ok=true`; fresh status возвращает `ok=false` и соответственно tombstone_matches/conflicting_receipts. Это текущий correctness-блокер интеграции WIP, который оба первых ответа ещё не знали. Узкая правка — синхронизировать view после copy, регрессии на exact/conflicting migration и повторный reconcile.

Подтверждён также P2 в cache: после замены родительского каталога событий symlink на внешнюю копию с теми же bytes внутри одной lock hold cached snapshot принимает запись, тогда как полный `read_path` отклоняет outside canonical storage. Условие — out-of-band структурная правка; обычный writer под lock его не создаёт. `_identity` должен сохранять проверку resolved boundary при reuse. Полный test suite и benchmark этими воспроизведениями не заменены.

## Совместный порядок

1. Сохранить baseline/WIP, исправить подтверждённые WP-20 дефекты, targeted recovery/cache tests, golden replay, полный `make check`, small/large benchmark. Исторические предупреждения doctor не удалять ради числа ноль.
2. Pin Codex CLI model и проверить builder/reviewer отдельно. Fixed IDs всего шесть (`model.py:50–56`): нельзя без schema work придумать `codex-sol-builder`/`codex-luna-builder`; при смене модели под одним ID qualification перезаписывается. На первую волну один builder pin Sol и один reviewer Astra, Claude — отдельная независимая проверка. Luna/Grok подключать по eval, не по предположению об экономии.
3. Контракт результата и постоянный agent entry: provenance, task/run links, result slots, сохранённые версии, пагинация, честные состояния, review конкретной binding; параллельно быстрый CSS-fix completed.
4. Карта: focus до capacity gate, objective/application groups, реальные boundary prerequisites, keyboard/list, переходы task↔result. Никаких выдуманных процентов или сроков.
5. Один вертикальный browser сценарий на настоящих результатах, включая restart/history/expired/error; затем единая сборка assets, wheel smoke, exact review и человеческая acceptance. Полные macOS/Linux release gates остаются отдельным обязательством, без выдуманного прохождения из-за согласия двух ответов.

Готовность GPT-6 и рейтинг ролей остаются эмпирическими вопросами: механизм проверяет canary, качество — одинаковый representative project eval с terminal outcomes и исправлениями человека. API migration, двусторонний Linear sync и универсальный orchestration rewrite в эту последовательность не входят.
