Объединённый путь предлагаю такой:

1. **Зафиксировать границу уже доказанного.** Сохранить точную связь source, bundles, установленного MCP, профилей и receipts. 2. **Провести GPT-6 продуктовый пилот с эффективной конфигурацией.** Проверять agent override, модель, profile ID, назначение implementation/review, CLI и source identity. Astra имеет сообщённые успешные проверки обоих назначений; Sol сначала дал mismatch и needs_operator, затем диагностический успех. Второй результат не стирает первый и не заменяет продуктовый прогон. `model=null` на CLI 0.145 не доказывает GPT-6. Авторизация Claude/Grok разрешает проверку точных версий, но не устанавливает их качество. Luna остаётся гипотезой для ограниченных задач, пока нет соответствующих доказательств.

3. **Замкнуть долговечный результат и точную проверку.** Дизайнер публикует две сохранённые версии; frontend-агент — статический build и screenshot. Bound producer/task/delegation/content identity сохраняются, старые отсутствующие bytes обозначаются unavailable. После перезапуска результат открывается, просроченный preview остаётся просроченным. Проверка R2 не одобряет R1. Можно привязать existing review к точному manifest результата; новая универсальная сущность review не обязательна заранее. Превью получает отдельную границу доступа без переноса Commons credentials.

4. **Довести карту и масштаб по отдельным проверяемым задачам.** Dependency DAG оставить зависимостями; objective/application использовать для группировки. Канонические component/parent relations вводить отдельным контрактом, если пользователь должен ими управлять. Для сильного разработчика первичны переходы агент↔задача↔результат, причины отказа, keyboard и копирование ревизий. React Flow либо улучшенный SVG выбирать по проверяемому поведению. Диагностический профиль WP-20 указывает 6413 чтений при initial/post-append rebuild, но предложенное обновление после собственного append ещё не реализовано и не доказывает ускорение. Измерять его отдельно, сохраняя corruption/concurrency/retry guarantees.

5. **Закрыть обещание конкретным evidence.** Один настоящий frontend-run, независимое review точной версии, человеческая acceptance, EN/RU и узкий экран, корректные отрицательные состояния. После изменений backend — чистая переустановка и нужные canary. Linux/release evidence вести отдельными незакрытыми обязательствами. Ни согласие пяти ответов, ни число зелёных тестов не разрешают автоматическую приёмку, отмену задач или заявление о полном завершении.
