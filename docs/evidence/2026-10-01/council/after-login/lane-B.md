# Меморандум консилиума, 1 октября 2026. Перспектива: целостность продукта, приоритеты, опыт волн, доведение до результата

Источник: снимок HEAD `aa9d373` плюс незакоммиченные изменения. Приложение не запускалось, тесты не выполнялись, git недоступен. Всё ниже основано на чтении кода, планов, evidence и леджера.

## 1. Что реально есть, что сделано, чему научились

**Архитектура.** Продукт состоит из трёх слоёв: неизменяемый файловый леджер с проекциями, брокер, который запускает провайдерские CLI (Codex, Claude, Grok) как дочерние процессы с MCP-инструментами, и два собранных фронтенда: Work на React Flow и отдельная Gallery. Прямого API к моделям нет: Codex запускается как `codex exec` с флагом `--model` из профиля (`src/agent_commons/runtime/model.py:814-846`), ROADMAP относит API-провайдеры к отложенной стадии (`docs/ROADMAP.md:48-53`). Это принципиально для раздела о GPT-6.

**Доска и карточка агента.** Карточка агента на доске содержит четыре кнопки: Conversation, Results, Tasks, Give a task (`frontend/work/src/components/ProjectBoard.tsx:41-46`). Клик по самой карточке ничего не открывает. Кнопка Results появляется только когда сервер сообщил ненулевое число результатов (`frontend/work/src/components/OutputsPanel.tsx:54-57`); у агента без результатов «галереи» не существует даже как пустого состояния.

**Что показывает Results.** Это модальный диалог со списком, переключателем «последние/история» и опросом каждые 15 секунд (`OutputsPanel.tsx:61-108`). Принимаются только PNG/JPEG и live-preview на loopback-адресе (`src/agent_commons/services/outputs.py:41`, `frontend/work/src/outputsTypes.ts:85,110`). Для каждого элемента рендерятся заголовок, статус, состояние review и число версий (`OutputsPanel.tsx:100-106`), хотя DTO несёт producer_delegation_id, task_id, ревизии и сессию. Markdown, HTML, код, diff в Results не попадают вовсе. Пустое состояние звучит как «нет доступных изображений» (`frontend/work/src/i18n.json:926`).

**Live preview «работающего фронтенда».** Инструмент `commons_publish_live_preview` принимает только корневой origin на 127.0.0.1 с TTL от 60 до 3600 секунд, не проверяет достижимость и не запускает процесс (`src/agent_commons/mcp/live_preview_tools.py:45-58`, `src/agent_commons/runtime/live_previews.py:36-44`). Запись переживает успешное завершение прогона, но только до исходного expiry (`live_previews.py:126-171`). Провайдерский процесс стартует в новой сессии ОС, и при остановке брокер убивает всю группу процессов (`src/agent_commons/runtime/subprocess_runner.py:178,192,203`). Следствие: «превью фронтенд-инженера» живёт не дольше часа и только если dev-сервер пережил завершение прогона. Валидация 8 сентября уже видела превью stale после успешного завершения (`docs/audits/2026-09-08-project-native-collaboration-validation.md:57-63`).

**Чего воркер не может.** Набор MCP-инструментов воркера (`src/agent_commons/mcp/server.py:151-192`) не содержит регистрации артефакта, complete/submit задачи или привязки файла. Единственные пути публикации результата: `commons_publish_design_image` для PNG/JPEG и `commons_publish_live_preview`. Догфудинг 21 сентября это подтвердил: BASE.md создан, но зарегистрирован оператором через CLI, Results для него не появился (UX-26, UX-28 в `docs/handoffs/2026-09-21-blizhe-dogfooding-feedback.md:395-421`).

**Отдельная Gallery.** `/gallery` показывает Design Packages с точным происхождением экранов (`src/agent_commons/services/design_gallery.py:60-98`). Из Work на неё нет ни одной ссылки: ключи `project_open_gallery` и `library_open_gallery` есть в реестре строк, но ни один компонент их не использует. Руководство честно говорит, что Gallery «остаётся по адресу /gallery» (`docs/user/en/README.md:309`).

**Граф задач.** Вкладка «Карта» рисует собственный SVG: ранги по топологической сортировке, по четыре узла в ряд, лимит 128 задач, иначе список (`frontend/work/src/taskGraph.ts:8,80-87`, `frontend/work/src/components/TaskViews.tsx:98-108`). Узел несёт состояние, название, роль, фазу прогона (`TaskGraph.tsx:41-48`). Нет зума и панорамирования, нет группировки по цели или применению шаблона, хотя DTO уже несёт `objectiveId` и `applicationId` (`frontend/work/src/contracts.ts:407-408`), нет прогресса по группе, нет экспорта. React Flow уже стоит в бандле для доски, консилиум 21 сентября рекомендовал перевести на него и карту (`docs/handoffs/2026-09-21-council-product-direction.md:94`).

**Сделано по планам.** Волны 1–3 закрыты и приняты (`docs/plans/2026-09-09-ux-closure-tech-plan.md:632-765`). Из волны 4: WP-40 и WP-41 приняты 22 сентября, WP-20 прошёл два из трёх запусков, задача остаётся `ready` (TASKS.json, `task.3PA74TA6FF1WWPRYNRXHD8G68N`). Результат WP-20 на малом профиле:

Цель D-16 (≤1 с на 3 206 событиях) не достигнута, ADR 0023 в статусе черновика (`docs/adr/0023-incremental-ledger-validation.md:4`).

**Не сделано, хотя документы могут создавать иное впечатление.** Legacy-панель `index.html` всё ещё в дереве (C6 не выполнен), а она остаётся единственным местом, где виден sanitized stderr прогона: сервер пока не отдаёт поле диагностики в run-DTO, раскрытие в Work инертно (`docs/evidence/2026-09-22/wp-41-source-manifest.json:79`). CHANGELOG Unreleased заканчивается волной 2 (`CHANGELOG.md:14-40`). В леджере среди девяти `ready` задач пять августовских (DAG/routing/council, orient, evals, L1, R2), это не текущий backlog, а неразобранный хвост. Ни один кадр V01–V14 и ни один пользовательский сценарий так и не сданы (`docs/plans/2026-09-18-consolidation-and-wave-4-plan.md:38-41`).

**Опыт, который нельзя повторять.**
- «Аддитивное» поле сервера ломает строгий парсер клиента; backend и client половины DTO идут в одном пакете (finding.017DAF…, интеграция волны 3).
- Любая правка `src/agent_commons/**` инвалидирует квитанции всех профилей; после backend-пакета обязательны переустановка tool и canary именно для следующих профилей (план J.7, `2026-09-09-ux-closure-tech-plan.md:793-812`). UX-29 показал, что UI называет это «проверочный запуск завершился ошибкой».
- Grok трижды выходил без терминального вызова (finding.1JSG…, 4Y9B…, 7WED…); его работа каждый раз требовала ручной верификации координатором.
- Независимый reviewer требует заранее открытого review request, иначе попытка сгорает (finding.3XK0…).
- Параллельная hygiene-сессия с устаревшей expected_revision остановила все записи в леджер; перед reopen/cancel проверять неприменённые переходы (план, строки 130-153).
- Песочницы воркеров не запускают node/uv; проверка всегда у координатора, воркер обязан честно вернуть needs_operator.
- Запуск review до уведомления субагента срывается по snapshot guard (WP-41).
- Evidence трёх волн: только JSON-манифесты, скриншотов никто не сдавал.

## 2. Блокеры и целевой UX для технических пользователей

**P0.**
1. **Результат агента не доходит до его галереи.** Воркер не может зарегистрировать не-изображение; Results не умеет файлы; живое превью умирает за час. Для «фронтенд-инженер показывает работающий фронтенд» в коде нет пути, который переживёт конец прогона. Файлы: `mcp/server.py:151-192`, `services/outputs.py:41`, `live_previews.py:36-37`.
2. **Ни один реальный прогон на текущем main не доведён до принятого результата.** WP-40/41 закрыли UX-19/21/10 по тестам, но после них не было ни одного догфудинга; BASE в Blizhe не принят (`2026-09-21-blizhe-dogfooding-feedback.md:484-488`). L1 не доказан (`docs/ROADMAP.md:13-16`).
3. **Дрейф квалификации блокирует любую длинную сессию.** Смена установленной сборки превращает qualified-квитанции в «failed» без различения причин (UX-29, строки 423-431 отчёта). Это бьёт и по владельцу, и по координатору после каждого backend-пакета.

**P1.**
4. Карта задач не читается как блок-схема: нет групп, прогресса, зума, экспорта.
5. Диагностика остановки: сервер не эмитит stderr-хвост, Work показывает только код причины; удалять legacy-панель (C6) до этого нельзя.
6. WP-20 run 3 и повторный бенчмарк на большом профиле; иначе запись на 3 206 событиях остаётся десятками секунд.
7. UX-27 (скрытый отрицательный review, нет возврата) предположительно закрыт WP-10: карточка решения имеет `return_for_revision` (`frontend/work/src/components/DecisionCard.tsx:24-27`), но догфудинг шёл на другом бандле (`work-BBA7jVsK.js` против текущего `work-xeLYWBKN.js`). Нужна проверка на main, не предположение.
8. Гигиена: пять августовских `ready` задач отменить как superseded; CHANGELOG дописать; ADR 0023 перевести в принятый или отклонённый.

**Галерея агента: точная спецификация.** Не модальное окно, а экран `view=results&agent=<id>` (allowlist маршрутов уже в `frontend/work/src/appRouteState.ts:1-18`, добавить одно значение). Клик по карточке или по иконке агента открывает его. Структура экрана:
- Шапка: имя агента, специализация, профиль и модель, ссылка на задачи агента, одна primary-кнопка «Дать задачу».
- Лента результатов, последняя версия сверху, у каждого элемента: тип (изображение, живое превью, файл), задача-источник со ссылкой в инспектор, ревизия задачи, прогон, состояние review (`awaiting/approved/returned`, уже в DTO), число версий и переключение версий внутри карточки.
- Раскрытие «происхождение» с ULID задачи, делегации, сессии, content_revision, кнопка копирования. Это уже есть в DTO, терять нельзя.
- Живое превью: обратный отсчёт до expiry, статус «сообщено ready / истекло», кнопка «открыть» только пока ссылка допустима (`outputsTypes.ts:132-138`), подсказка «переопубликовать новым прогоном».
- Пустое состояние с действием: «У агента нет результатов. Дайте задачу или попросите опубликовать результат из прогона». Кнопка Results на карточке должна существовать всегда, с нулём.
- Ошибочные состояния по кодам: `outputs_unavailable`, `outputs_bounds_exceeded`, `outputs_scope_not_found` (`services/outputs.py:62-65,150,214`), каждая с одной причиной и одним действием, в обеих локалях.
- Для дизайнера: те же карточки, плюс ссылка в `/gallery?project=` на пакет, если экран входит в Design Package. Gallery должна наконец получить ссылку из Work.

**Карта задач: точная спецификация.** React Flow вместо собственного SVG, чистая функция раскладки остаётся в `taskGraph.ts` и тестируется отдельно. Узел: состояние, название, роль/модель, фаза прогона, число результатов. Рёбра зависимостей: сплошные для удовлетворённых, пунктир с меткой «ждёт» для блокирующих, красные для `prerequisiteMissing`. Рамки-группы по `applicationId`/`objectiveId` с заголовком цели и прогрессом «принято N из M», принятое считается только по acceptance. Клик открывает инспектор рядом, не уводя с карты; двойной клик открывает задачу. Режим «фокус на связанных» сохраняется. Экспорт Mermaid/DOT одним read-only эндпоинтом (консилиум §4, п. 4). Лимит рендера 128 остаётся, выше него список; серверные границы 512/4 096 (`src/agent_commons/domain/execution_plan.py:12-13`) уже позволяют такой граф. Клавиатурная навигация и legend обязательны, как сейчас.

**Что ценно технически сильным вайб-кодерам и что не упрощать.** Сохранить ULID, ревизии и канонические значения в раскрытиях, не вычищать их. Добавить: deep-link на любую задачу и агента (уже есть), палитру команд, показ эквивалентной CLI-команды рядом с действием (register/reopen/canary), экспорт графа, видимые typed-коды отказов. Не делать: прятать stderr-диагностику целиком, заменять статусы иконками без текста, «автозапуск» из шаблона.

## 3. Пакеты, первый инкремент, модели, риски

**Пакеты.** Исполнители по сложившейся схеме: Opus = `claude-builder` для фронтенда; Terra = `codex-builder` для backend/DTO; Astra = `codex-independent-reviewer`; Claude-reviewer для Terra; механика после замены Grok, см. ниже.

| # | Пакет | Исполнитель → review | Зависит от | Приёмка и проверки |
| --- | --- | --- | --- | --- |
| P-1 | Квалификация без ложного «failed»: состояния `failed/missing/runtime_changed/invalid`, сохранение даты прошлого успеха, кнопка canary в Settings, квитанция по паре профиль+модель | Terra → Claude | нет | тест на каждое состояние; UI показывает причину и расход; `make check` |
| P-2 | Передача файла-результата: воркерский инструмент регистрации bounded-файла (md/txt/json/html/diff) с точной привязкой к задаче и делегации; `kind: "file"` в outputs DTO; безопасный просмотр как текст, без рендера HTML; download-маршрут | Terra → Claude; клиентский парсер в том же пакете | P-1 | сценарий «BASE.md виден в Results задачи и агента»; тесты present/absent/refusal; ни одного пути в DTO |
| P-3 | Экран галереи агента по спецификации выше, Results с нулём, ссылка на /gallery | Opus → Astra | P-2 (для файлов), изображения можно раньше | кадры EN/RU/узкий; keyboard; тесты `outputs.test.mjs` |
| P-4 | Диагностика: сервер эмитит bounded stderr-хвост в run-DTO; затем C6, удаление legacy-панели | Terra → Claude, потом C6 | нет | раскрытие в Work показывает хвост; wheel без index.html |
| P-5 | Карта на React Flow с группами и прогрессом; экспорт Mermaid/DOT | Opus (UI) + Terra (эндпоинт) → Astra | нет | `task-graph.test.mjs` переписан; 300 задач без двойного рендера; a11y |
| P-6 | WP-20 run 3 и бенчмарк на 3 206 событиях | Terra → Claude; бенчмарк: механик | нет | таблица фаз, `doctor` и golden replay неизменны |
| P-7 | Гигиена: отмена пяти августовских ready, CHANGELOG за волны 3–4, статус ADR 0023 | координатор | нет | `task list --state ready` только живые пакеты |
| P-8 | Пилот GPT-6, см. ниже | координатор + Terra для поля effort | P-1 | canary и representative eval зелёные |

Порядок: P-1 → P-7 параллельно → P-2 → P-3 → P-4 → P-5 → P-6; P-8 стартует canary-частью сразу после P-1.

**Минимальный первый завершённый инкремент.** Один реальный прогон на текущем main в синтетическом проекте: агент-«frontend engineer» на `codex-builder` делает статическую страницу, публикует PNG через `commons_publish_design_image` и живое превью, владелец открывает Results с карточки, независимый reviewer одобряет, владелец принимает. Этот путь существует в коде сегодня и уже проходил у Codex 8 сентября (`2026-09-08-project-native-collaboration-validation.md:52`). Критерий: кадры EN/RU экрана Results и карточки решения, запись `task.accepted`, список найденных дефектов превращён в задачи. Без этого инкремента все пакеты выше строятся на непроверенном фундаменте, что уже было в волнах 1–3.

**План GPT-6.** В проекте модель задаётся двумя способами: полем `model` в профиле (`runtime/model.py:1232-1241`) и моделью нанятого агента, которая подменяет модель профиля при запуске (`services/roles.py:28-43`, `services/delegation_runtime.py:1020-1043`). Значит, миграция на GPT-6 это пин модели, а не переход на API; Responses API, temperature и logprobs к проекту не относятся. Что требуется:
- Поле `reasoning_effort` в Codex-профиле с закрытым набором `low/medium/high/xhigh/max`, передаваемое как `-c model_reasoning_effort=…`; флаг `--strict-config` уже используется. Поддержка этих значений и идентификаторов GPT-6 в Codex CLI 0.145 здесь не проверена, это первое, что должен подтвердить canary.
- Квитанция квалификации включает модель (`runtime/provider_qualification.py:170`), но хранится по профилю, поэтому два агента с разными моделями на одном профиле вытесняют canary друг друга (план J.2). P-1 обязан ключевать квитанцию по профилю и модели, иначе Sol и Astra на `codex-builder` будут постоянно «не квалифицированы».
- Распределение ролей: Astra как `codex-independent-reviewer` с высоким effort для review и ADR; 6.1 Sol как backend builder взамен Terra; Luna на механику и бенчмарки взамен Grok, который трижды не вызвал терминальный инструмент. Claude Opus остаётся на фронтенде, Claude-reviewer проверяет Codex-работу для кросс-провайдерной независимости.
- Representative eval, а не бенчмарки: в scratch-worktree повторить вслепую один принятый backend-пакет (WP-12.1, eligibility DTO) и один review-раунд, где Astra нашла дефект ревизии в WP-10. Мерить: прохождение named tests, нахождение подложенного дефекта, вызов терминального инструмента, время до результата, число попыток. Каждая пара «профиль × модель» квалифицируется отдельно, прошлые canary не считаются.

**Риски и несогласие.**
- Пакет P-2 расширяет MCP-поверхность воркера на запись файлов в леджер; это противоречит прежней позиции «воркеры читают, пишут только терминальные инструменты» (finding.6D4SW…). Я считаю, что без этого продуктовое обещание «результат на карточке агента» невыполнимо; альтернатива «владелец регистрирует через CLI» доказанно не работает для целевого пользователя.
