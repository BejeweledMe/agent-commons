Точный профиль: gpt-6-astra, официальный временный Codex CLI 0.159.3, installed MCP source SHA fab6f03a9ca61162e4495cc8758c662cf4720a7588d7cbee169b8e2c4dcc274e.

Preflight прошёл. Новый state root потребовал собственную qualification: exact canary успешно завершился за47.208s, canonical succeeded, child closed, terminal1/1/0, mismatch=false. Это всё ещё только compatibility evidence.

При первоначальной настройке исправлены два отказа до provider work: root-path claim запрещён (заменён точными путями), а selected commons-start требовал explicit operator catalog (предоставлен temp catalog; attempts перед настоящим запуском был пуст). CLI profiles честно оставляет authentication not_checked: этот read-only command не получает auth snapshot, поэтому launchable=false не доказывает отказ реального провайдера; qualification была current/qualified, actual broker запустил процесс.

Первый продуктовый запуск: delegation.7N5GQV8KWYTJWTKMSTNSQ41SCP, attempt.0MAFPYJ9B9CP37X2MJRQ1AG523,73.343s, provider exit0. Canonical needs_operator/invalid_result, mismatch=true; terminal2 calls/1 completion/1 rejection. Один commons_delegation_needs_operator был отклонён по ValidationError, после него worker честно записал input_needed; broker завершил как needs_operator. Исходные события и result сохранены неизменными, безопасная копия результата — attempt-1/.

Конкретная причина, записанная worker: нет agent-commons на PATH; доступный обычный Python не импортирует agent_commons; обязательные doctor/session/claim startup checks недоступны через scoped MCP. Отдельная проверка координатора подтвердила: shutil.which('agent-commons') == None, но фиксированный installed executable существует и выполняет --read-only doctor успешно. Product source files, build, PNG и outputs отсутствуют: обе task/agent projections пусты. Child и parent закрыты; claim освобождён. Это не evidence неспособности модели создать frontend.

commons-start был выбран координатором, но не является произвольным препятствием: generated implementation instruction (services/delegation_instruction.py:105) прямо требует onboarding и commons-start. Та же инструкция явно говорит, что child session уже создана брокером. Сам skill требует session start только при отсутствии активной explicit session; создание дополнительной session не нужно. Поэтому skill не удалён и правила не обходятся.

Есть ещё несовместимость первоначального task wording с generated terminal contract: task просил artifact в result_refs, а generated implementation protocol фиксирует result_refs=[task:<exact target>]. В новой task revision это исправлено: реальная PNG-публикация остаётся отдельным каноническим доказательством с точными artifact IDs/bytes; terminal следует фиксированному task-ref протоколу.

После отдельного разрешения root создаётся новая parent session и новая delegation (не resume, не blind retry).
