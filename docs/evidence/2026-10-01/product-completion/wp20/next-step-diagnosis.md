# WP-20: решение о следующем шаге после независимого прогона

Диагноз только по чтению frozen `/private/tmp/commons-product-wp20-20261001` (package SHA-256 `194b08d49721b375aa7858a7db67b787134ff0cd7dfc26d377163dd7bf45b866`) и независимого Grok benchmark/report из `docs/evidence/2026-10-01/product-completion/wp20/grok-verification/`. Новые tests/benchmarks/provider calls не запускались; исходники и основной ledger не изменялись. Номера строк ниже относятся к frozen source, не к движущемуся объединённому checkout.

**Решение:** принять own-append/RLock как отдельный проверенный шаг, не расширять его до обещания ≤1 s. Следующий bounded patch может включить только два простых устранения повторной работы ниже. После отдельного review и неизменённого six-workload benchmark решить, оправдан ли небольшой внутренний refactor receipt derivation. Cross-lock caching и receipt-view reuse после append требуют отдельного дизайна и набора доказательств.

## Два безопасных кандидата следующего bounded patch

1. **Не строить snapshot для явно пустого evidence.** `tasks.py:237` отличает `None` («сохранить прежние bindings») от явной последовательности («заменить»). Однако пустая последовательность идёт в `_bind_evidence_refs, manager.py:930`, который вызывает `snapshot()` до проверки refs. В `complete_task`/`submit_task` это происходит до `record_event`, когда lock-scoped view ещё нет. Поэтому штатный benchmark с `artifact_refs=()` читает events/manifests и делает projection дважды.

   Минимальное изменение — в ветке `artifact_refs is not None` вернуть `[]`, если последовательность пуста; непустой список и `None` оставить как есть. Либо общий early return внутри `_bind_evidence_refs`, но тогда требуется проверить всех callers. Первый вариант уже по scope и проще для review. Последующий `record_event` всё равно выполняет весь `_guard_integrity`, lifecycle CAS, policy и receipt validation внутри canonical lock; проверка ledger не исчезает. Не заменять эту ветку общим `if not artifact_refs`, иначе `None` потеряет смысл сохранения evidence.

   Проверки: explicit-empty complete/submit делает один pre-append snapshot/один replay и обычное полное чтение; повреждённый прежний event всё равно отвергается; `None` сохраняет binding и отказывает при stale evidence; непустые refs сохраняют точную revision binding; stale task revision/concurrent writer по-прежнему отвергается. Результат, который можно обещать по коду: убирается **один внешний полный read/replay** для этих двух пустых-evidence операций. Новое время пока не измерено. На create/take/decision/HTTP create это не влияет.

2. **Убрать лишнюю `_identity` перед неизбежным `_verify`.** В `_refresh, manager.py:150` raw read/hash/resolve выполняется даже при `rebuild=True`, после чего `_verify` опять делает identity-before, validating `read_path`, identity-after. При rebuild или отсутствии cached entry можно сразу вызвать **неизменённый** `_verify`; дешёвое сравнение identity нужно лишь тогда, когда действительно возможен reuse.

   Это не stat-only cache и не пропуск проверки файла: `_verify, manager.py:174` сохраняет все три шага и три попытки, normal cache-hit refresh продолжает читать/хешировать каждый file. На исходном large fixture первый полный refresh избавится от одного лишнего raw read/hash/resolve на каждом из 3556 прежних canonical files. Число полных `read_path` останется прежним — для измерения нужен отдельный счётчик `_identity`/raw bytes, а не обещание уменьшения canonical read_calls.

   Проверки: existing TOCTOU и changed-parent-path regressions, same-size/mtime corruption, symlinks, unexpected add/delete, schema/policy rejection, nested hook. Не объединять этот шаг с изменением `_identity`, containment или before/after sequence. Доля выигрыша не измерена; она находится внутри части lock-hold residual, а не равна всему этому residual.

## Малый refactor receipt derivation, только отдельным шагом

`ReceiptRecovery._event_map:63` повторно выводит для каждого record canonical-relative path, key digest и semantic hash. В обычном write карта строится в preflight `status`, затем в `reconcile`, затем ещё раз в финальном `status` из того же `reconcile` (`371–463`). Между двумя последними вычислениями неизменны переданные records и file_digests; меняются operational receipts/anchor.

Безопасный узкий refactor: private status helper принимает **уже вычисленную карту только от этой invocation reconcile**, а публичный `status` продолжает строить её сам. Anchor/scope/migration/receipt checks и их порядок остаются. Не переносить карту через append, refresh или lock release и не использовать её вместо перечитывания operational state. На обычном write устраняется одно построение примерно 3207 event-info entries, но оба `load_recovery_view` остаются. Восстановительные пути должны проверяться отдельно: missing receipt, bootstrap/migration, legacy orphan, abandonment/reconciliation mismatch, crash после anchor и после publication. Старый cProfile не даёт допустимого точного wall-time выигрыша для нового шестинагрузочного прогона; нужны новые granular counters перед оценкой.

## Что нельзя просто «переиспользовать»

- **Receipt snapshot через append.** Сейчас `prepare_for_write:474` и `reconcile:380` независимо читают view. Между ними EventStore.reserve публикует receipt; trusted hook способен выполнить nested write; corruption/migration/abandonment должны остаться видимыми. `load_recovery_view:429` проверяет scoped reservations, tombstones, reconciliation-to-tombstone hash и path containment. Нужен собственный lock-scoped verified receipt view с перечитыванием bytes/path set, identity binding, проверкой собственного append и conservative fallback. Нельзя просто передать preflight dict в post-append reconcile.
- **Validated canonical cache через lock release.** Новый hold намеренно заново валидирует все canonical files. Reuse требует явной политики lifetime/invalidation по schema reload/extensions, content-policy configuration, source/semantic-validator version и resolved containment, плюс fresh byte hashing и structural-change fallback. Public schema mapping и `SchemaRegistry.reload()` не позволяют бездумно привязать cache только к event hash. Persistent SQLite/anchor не могут сами считаться доказательством полной validation: derived state остаётся неавторитетным. In-memory warm-cache не решит process-/manager-cold workload автоматически.
- **Изменить storage layout или trusted writer model.** Packed ledger/manifest, incremental authenticated state, перенос полной проверки с write path меняют контракт storage/trust/recovery и требуют отдельного ADR, миграции, threat model и crash/concurrency review. Это не продолжение двухстрочного fast path.
- **Ускорить сами validators.** `SchemaRegistry.validate:96` создаёт validator/FormatChecker на каждый вызов; `policy.scan:408` сканирует весь документ. Возможны отдельные оптимизации construction/repeated text classification с точным сохранением всех findings, limits, locations, schema reload semantics и безопасности потоков. Но нынешние phase totals не отделяют construction от traversal/regex/JSON/I/O; выбрать подход или обещать ускорение без профиля нельзя. Удалять проверки по «уже знакомым» fields или доверять projection вместо canonical validation нельзя.

## Измеренный предел выводов

Независимый прогон: create cold 8.558 s/warm 8.696 s; complete 13.233/13.291 s; submit 13.169/13.216 s. У create cold canonical validation 3.897 s, receipt preparation 1.133 s, reconcile 1.501 s, exclusive lock_hold 1.595 s, projection 0.358 s. Это exclusive-фазы; lock_hold здесь residual внутри critical section, не пользовательская latency.

При **условном** полном исчезновении обоих receipt phases, без изменения остального measured path, арифметический остаток create ≈5.924 s. При полном исчезновении canonical validation **и** обоих receipt phases он всё ещё ≈2.027 s. Это Amdahl-style разложение одного шумного прогона, не прогноз нового кода и не фундаментальный нижний предел. Поскольку proposed small patches не устраняют первичную canonical validation, нынешние 3.897 s этой фазы сами превышают всю цель ≤1 s. Ускорение complete/submit нельзя выдавать за достижение общего WP-20 gate.

Практический ceiling текущего bounded подхода: доказуемо убрать лишний scan у complete/submit, лишний raw identity read при rebuild и, отдельно, одно derived-event-map построение; **не обещать никакой новой секунды до benchmark**. Следующий decision gate — тот же immutable large benchmark (все шесть mutations, тот же cold/warm protocol), counters per identity/read/map/load, exact source hash, focused crash/retry/concurrent/security tests и интегрированный `make check`. После этого либо принять ещё один ограниченный выигрыш, либо открыть отдельный дизайн low-latency write path. ≤1 s остаётся открытым требованием, не причиной ослаблять every-byte validation.
